# Task Response Steering Contract

Use this reference when adding or auditing terminal support for steering an already-running task response.

- Verify the current backend handler and thread template before coding. The steering endpoint is an HTML/form contract, not an assumed JSON API: `POST /tasks/<taskID>/thread/steer` with selected `project_id`, `message`, and the exact `expected_turn_id`; parse the returned fragment's stable `data-thread-input-id` for acknowledgement identity.
- Establish the active turn from a project-scoped thread read. First collect every task-matching execution pair marked `data-execution-pair="true"` and `data-exec-status="running"`; then require exactly one candidate and require that candidate to carry one valid non-empty `data-exec-id`. Do not filter out malformed running candidates before counting: one valid ID plus one running pair with a missing, duplicate, conflicting, or otherwise invalid ID is ambiguous and must fail closed locally. Zero, multiple, or malformed candidates must be actionable errors. Never guess a turn, use a stale cached turn, or fall back to ordinary reply after a guard failure.
- Preserve backend stale-turn behavior. Surface HTTP `409` as a nonzero conflict with recovery guidance and issue no retry or unguarded ordinary-reply mutation.
- Keep project scope in every read and mutation and test a non-default project, URL/path escaping, exact form fields, active-turn propagation, no-active rejection, malformed/multiple-active rejection, and stale-conflict handling.
- For live-thread visibility, inspect the actual backend handler/template/event publisher at the delivered integration ref and verify the event name, payload identity, and response-fragment semantics. A test that injects a guessed SSE event directly does not establish that a successful steering POST will refresh an open thread. Either consume a verified backend event after validating task/project ownership or use the successful returned fragment/control-plane refresh; add a regression that exercises the real acknowledged mutation-to-visible-thread path and preserves ordinary pending-reply identity distinctions when multiple inputs are in flight.
- If pending-input listing, cancellation, or queued-input steering is not implemented, explicitly document active steering as the release boundary rather than implying pending-input parity.
