# Model Edit Details Contract

Use this when changing existing model/provider configurations in the backend or a Go client, CLI, or TUI.

- `GET /models/:id/edit-details` is the authoritative snapshot used to build the full-form `PUT /models/:id` update. Return every persisted field whose omission causes a destructive default, not merely fields exposed in ordinary model lists.
- For OpenAI-compatible providers, `default_max_tokens` must be included explicitly and the client must preserve it on an edit. The current backend update normalizes an omitted or nonpositive form value to `0`; do not replace a missing detail value with a guessed default.
- If an older backend omits `default_max_tokens` for an affected configuration, fail before the `PUT` rather than risking a reset. Resolve it by adding the authoritative backend response field, or by an explicitly revised non-destructive product contract.
- Do not classify a custom-auth field as safe solely because it is scalar. An arbitrary `access_token_prefix` can embed a static credential, and custom URLs may carry userinfo, query, fragment, or path-embedded credentials. Do not return an ambiguous custom-auth scalar unless its stored values are constrained to a demonstrably secret-free form.
- For API-key OpenAI-compatible edits, prefer server-side preservation over a custom-auth projection: omit `custom_auth_config_json` entirely from edit details, including discovery fields, prefixes, URLs, secrets, and maps. The terminal must submit the explicit `model_edit_preserve_custom_auth=on` marker and no `custom_*` form fields. The backend must honor that marker only for non-OAuth/API-key updates, retaining the complete stored custom-auth configuration.
- Do not use preservation as a validation bypass. Revalidate the new base URL against the stored `AllowPrivateEndpoints` policy, and enforce the server private-endpoint policy, whether the request rebuilds custom auth or preserves it. OAuth and browser flows that intentionally edit custom auth retain their normal explicit-field behavior.
- For any safe scalar projection that remains necessary, build it from a strict allowlist. Omit signing secrets and arbitrary header/parameter maps, including static, token, and refresh headers or parameters. Preserve omitted values server-side when their corresponding form keys are absent, rather than resetting them during a partial terminal edit.
- The full-form handler must preserve protected custom-auth values when their form fields are absent, and the client must omit protected fields rather than submit empty values. In particular, never synthesize an empty signing-secret field from a sanitized detail response; an explicit clear control remains the only clearing path.
- Keep only safe detail fields in non-rendered client state and serialize only fields allowed by the selected update contract. Terminal output, command history, JSON results, logs, and errors must never include omitted values or credentials.
- Add backend handler and client/terminal round-trip regressions for a custom API-key configuration with non-default `models_array_path` and `model_id_field`. For the server-preservation contract, verify edit details contain no custom configuration, a partial edit sends only the preservation marker, and persisted configuration retains discovery and protected settings.
- Include secret-exposure regressions for every omitted scalar class, at minimum a sentinel-bearing access-token prefix and query-bearing refresh/profile URLs. Assert neither sentinel appears in edit details, terminal output, history, errors, or JSON; then prove a partial edit preserves each omitted persisted value without submitting it.
- Add a backend handler regression that creates a compatible configuration with a nonzero token cap and verifies the edit-details JSON round-trips it. Keep client/terminal transport coverage that decodes the real `default_max_tokens` shape and verifies the subsequent full-form update retains the value.

When backend changes are in scope but its primary checkout has unrelated work, inspect it read-only and use a clean isolated task worktree for the minimal contract fix. Integrate the required backend commits through a clean branch based on backend `main`, prove that ancestry, and validate backend and client commits independently; do not treat validation of one repository as validation of the other.
