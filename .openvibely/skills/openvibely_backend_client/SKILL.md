# OpenVibely Backend Client Integration

Use this skill when building, debugging, or extending a Go client, CLI, or TUI that talks to the OpenVibely backend (`github.com/openvibely/openvibely`). Verify current routes and payloads from backend source, templates, or generated Swagger before relying on remembered behavior.

For historical open findings and settled implementation patterns, load `references/openvibely-terminal-finding-log.md` only when auditing parity, performance, JSON output, redundancy, or previously filed findings.

## Backend Integration

- Resolve and record the client and backend repository roots before editing. If changes are limited to the client repository, do not edit, generate files in, build, or test the backend repository.
- The Echo HTTP server commonly defaults to port `3001`. Machine-facing JSON includes `/api/projects`, asynchronous chat at `/api/chat/message`, capacity/analytics endpoints, and current routes documented in Swagger.
- For asynchronous chat, POST returns `201` with an ID; poll `GET /api/chat/message/:id` until `completed`, `failed`, or `cancelled`.
- Queued API chat can return a queue/thread-input ID first, then promote that input to a new execution ID. Verify the backend promotion and status contract: a status lookup by the original queue ID may later return the promoted execution's terminal status and `message_id`, while `chat_response_done` may carry the promoted `exec_id`. Preserve a correlation mapping or alias from the accepted queue ID to the promoted execution ID; do not stop polling or reject completion merely because the identifier changes. Add an acceptance → promotion → completion regression covering both polling and SSE paths.
- Consume real-time task, chat, and file-change events from `GET /events/live`. Use context cancellation and capped reconnect backoff. Treat SSE completion as an acceleration signal, not a replacement for polling.
- Authentication is optional and cookie-session based. For mutation/auth classification, treat only HTTP `401` or a redirect whose parsed `Location` URL has the exact path `/login` as authentication required; do not use a string prefix that also matches `/login-help` or `/login2`. Preserve any separate bare-`302` compatibility required by documented read routes rather than sharing that broader classifier with mutations.
- There is no general Go client SDK in the backend repository. Mirror machine-facing request/response structs field-for-field from current Swagger or handler source.
- For project-scoped JSON endpoints, verify how the backend resolves project context, not just the path. Lifecycle endpoints `GET /tasks/:id/lifecycle-executions` and `GET /lifecycle-executions/:id/events` use `project_id` query context to authorize and resolve the task or execution; client methods must accept and forward the selected project ID rather than relying on server-side preference or first-project fallback. Add a contract test with a non-default project that asserts `project_id` on both requests and successfully reads that project's records.

## HTML And HTMX Routes

- Do not assume `Accept: application/json` makes web routes JSON. Confirm the handler has an explicit JSON branch such as `wantsJSON(c)`; `/tasks` may return HTML even with a JSON Accept header.
- For web-only resources, inspect `internal/handler/handler.go`, the relevant handler, and `web/templates/**/*.templ`. Reuse stable semantic attributes such as `data-task-id`, `data-task-status`, `data-alert-id`, `data-skill-handle`, or `data-automation-card-*` rather than CSS classes or visual layout text.
- When a page exposes structured resource cards, parse one record per card and use those records for list rendering, filtering, reference matching, JSON output, and post-mutation refreshes. Keep `pageText`/whole-document text extraction as the prose fallback only when structured attributes are absent. Preserve state precedence for malformed cards and test active/paused rows, full IDs, empty-state guidance, unchanged JSON shape, one-GET list behavior for non-paginated routes, and mutation refreshes.
- For enum-like lifecycle badges in structured cards, keep the canonical recognized-label/rank mapping in one helper. Make badge recognition delegate to that rank function instead of repeating a status switch, and use table-driven parser regressions for every recognized state, unrelated labels, and multiple badges to lock in unknown-label handling and precedence without changing traversal or mutations.
- Implement HTML transport and parsing in the client package, not command handlers. Parse with `golang.org/x/net/html`, preserve IDs from `data-*`/`hx-*` attributes, and render prose-heavy pages as cleaned text only when no structured attributes exist.
- Do not derive a card title from the first text line. Menus and controls may precede content. Select title-bearing elements structurally, prefer semantic attributes, exclude action/deep links such as `tab=`, and prevent nested child links from replacing the parent title.
- Match browser mutations exactly: verify method, route, query parameters, form fields, expected status, and whether the handler branches on `HX-Request: true`. Send the HTMX header when needed to receive the successful fragment/no-content response instead of a redirect.
- When auditing mutation transport redundancy, compare form-encoded, JSON, and multipart paths as one responsibility: request construction, `HX-Request`/`Accept` headers, execution, authentication classification, success-status checks, and API-error conversion are shared-consolidation candidates. Use a narrow private helper or shared policy only after preserving intentional transport differences; in the current client, form mutations distinguish non-login redirects with a specific error while JSON and multipart paths retain generic API-error handling. Add request-level regressions for each transport, exact `/login` redirect and `401` handling, successful `2xx` variants, representative API errors, and the preserved redirect distinction before and after consolidation.
- Keep `httptest` fixture clients' redirect policy identical to production: if the production client disables redirects, set `CheckRedirect` to `http.ErrUseLastResponse` on every custom fixture client. Go's default redirect-following behavior can consume a `3xx` and hide exact-login versus ordinary-redirect classification; assert no-follow behavior and the final status/location directly.
- For task attachment management, treat the backend as an HTML/HTMX contract rather than a JSON API: verify the upload route, repeated multipart field name, delete route, project query, response fragment, and stable row/control attributes from the current handler and template. The established task flow uses `POST /tasks/<taskID>/attachments?project_id=<selectedID>` with one multipart `files` part per local file, returns the `#attachment-list` fragment, and deletes with `DELETE /attachments/<attachmentID>?project_id=<selectedID>`. Parse stable attachment IDs, filenames, and byte sizes from the fragment in the client package and use the refreshed fragment after mutations.
- Treat project scope as a response invariant as well as a request parameter for attachments. Require a selected project before attachment reads or mutations, and reject a task page whose project marker or an attachment delete control's `project_id` does not match the selected project; never render a cross-project response as success. Add tests for non-default project queries, repeated `files` parts, refreshed rows, stable delete IDs, backend failures, and mismatched task/control scope.
- For skill mutations, mirror the backend's current JSON contract rather than reusing browser form encoding: create sends `handle`, `name`, `description`, `scope`, and `body`; edit accepts `body` and `scope`, but first inspect backend normalization because omitted metadata or defaulted state may be treated as replacement. Since `/skills edit` promises a body-only change, preserve existing `name`, `description`, and `enabled` state by resolving/listing the current skill and sending explicit values, or use an explicitly supported partial-update path. Do not omit optional booleans whose backend default changes the persisted state; editing a disabled skill must not silently re-enable it. Enabled-state writes send `enabled` and `scope`; always-use writes send `always_use` and `scope`. Set `Content-Type: application/json` while preserving `HX-Request: true` and `Accept: text/html, application/json`. For HTML/HTMX form mutations, accept only 2xx responses (`200` fragments and `204` no-content). Parse the `Location` header before classifying redirects and require the exact parsed path `/login` for an auth result; query strings may vary, but near-matches such as `/login-help` and `/login2` are ordinary unexpected redirects. Reject every other unexpected 3xx, configure the client not to follow redirects, and close response bodies on every path. For JSON and other transports, preserve their documented status contract while applying the same exact-path `401`/login-redirect classifier before broad success handling; do not reuse a read-route classifier that treats every bare `302` as authentication. A JSON POST with a non-login `3xx` must remain a normal non-2xx API result unless its endpoint explicitly documents that redirect as success. Treat the form-encoded asynchronous chat POST (`SendChatMessage`) as a mutation as well: use the mutation auth classifier so a bare non-login `302` is an ordinary API error, while `/login` redirects and `401` remain auth-required. Keep the login endpoint's documented success redirect (normally `/` or its requested destination) distinct from an exact `/login` failure redirect; other login redirects should be unexpected rather than silently treated as invalid credentials. Add focused coverage for login redirects across backend status variants, `401`, parsed exact-path matching, near-match paths, no redirect follow, valid fragments, `204` success, body cleanup, and intentionally accepted non-login redirects only where the transport contract requires them. Keep delete on its established transport unless the backend contract changes. Test by decoding raw request JSON and verifying persisted metadata and enabled/disabled state after updates, including a focused body-only edit of a disabled skill, with a handler that rejects non-JSON payloads in both client and TUI dispatch/contract coverage.
- Scope is part of a listed skill's mutation identity, not display-only metadata. When a list/card exposes `global` versus `project`, thread the resolved `Skill.Scope` through edit, enabled, always-use, and delete calls. Send the actual scope in JSON writes and the backend-required scope query/form field for delete; never hardcode `project` or omit scope because the selected resource happened to be rendered in a project list. Add a global-skill contract test that proves the request targets the global root, alongside the project-skill case, and verify persisted state rather than only request shape.
- Task review comments are web/HTMX resources, not native JSON API routes: list with `GET /tasks/<taskID>/reviews`, add with `POST /tasks/<taskID>/reviews`, and submit form fields `file_path`, `line_number`, optional `line_type`, and `comment_text`. Parse stable `review-comment-item` markup and `data-*` attributes in the client package, then reuse the parsed struct for terminal rendering and CLI `--json` output.
- Do not guess mutation routes from command/action names. Read the actual client method or backend handler before asserting paths. Known easy-to-guess-wrong examples include `ActivateBacklog` → `POST /tasks/backlog/activate`, `SweepCompletedTasks` → `POST /tasks/move-completed`, `SetSkillAlwaysUse` → `POST /skills/<handle>/always_use`, and Slack channel `remove` → `/channels/slack/disconnect`.
- Treat backend template attributes as a compatibility contract that can drift. Add fixture tests copied from representative current markup, including controls before titles and nested child links, plus dispatch tests that assert exact method, path, query, form fields, and HTMX headers.

## Paginated Card Lists

- Treat a structured-card HTML list as incomplete until the current backend handler/template proves it is non-paginated or has no continuation. A successful first response can still omit later cards; inspect the page-size, continuation query shape, and semantic pagination markup or headers instead of assuming one GET is complete.
- Put traversal in the shared HTML transport/client layer, not in individual TUI commands. Repeat the original project scope and filters on each continuation request, use the backend-advertised maximum page size where supported, preserve first-seen order, and deduplicate by stable semantic resource ID across pages.
- Prefer the backend's explicit continuation signal, such as `X-OpenVibely-Card-Page-Has-More`, together with semantic pagination-root attributes. An explicit `has-more: false` header must override stale or contradictory HTML attributes; do not continue indefinitely or stop early on inconsistent markup.
- Bound automatic traversal by both pages and aggregated cards. The current safe client bounds are 200 continuation pages and 10,000 cards; treat bound exhaustion as an error or partial result according to the existing command contract, never as a silently complete first-page result.
- Preserve resource-specific pagination semantics. Personality built-in cards are not paginated, while custom-card offsets count only custom cards, not the mixed built-in/custom rendering; do not advance offsets from the total number of rendered cards.
- For text-backed methods such as channels, automations, and personality, continuation responses may repeat the entire container, headings, controls, fixed cards, and pagination markup. Preserve the first page's full-container text once, then extract only nodes matching the first page's declared pagination-card selector and append newly seen card text in order, deduplicated by its declared pagination key; never concatenate whole continuation-root text.
- Apply the same pagination audit to successful HTMX mutation refreshes, not only ordinary GET list methods. A mutation response that re-renders a bounded list, such as an alert delete/read/action response containing only the first page plus pagination metadata, is still incomplete. Either traverse the continuation through the backend's documented list/fragment route while preserving project scope and filters, or perform an explicit full refresh before rendering; do not parse the mutation fragment directly into a final collection. Add a regression covering more than one page after mutation, continuation query and scope, order/deduplication, and continuation failure.
- A continuation request or parse failure must remain visible through the established partial/error reporting path rather than returning a successful-looking truncated collection. Keep empty collections non-nil so JSON output remains `[]`, and do not change public collection or JSON types while aggregating pages.
- Add client regressions for representative card families and every route covered by the backend contract. Assert later-page visibility, stable order, cross-page deduplication, selected-project/filter propagation, resource-specific offsets, empty results, and continuation failure. For text-backed routes, use realistic full-container continuation fixtures with repeated fixed content and overlapping cards. Confirm resources such as tasks or schedules are not swept into the paginator unless their current backend contract explicitly exposes the same card-pagination protocol.

## Command And Client Patterns

- New chained-verb resource commands should follow the established end-to-end pattern: add client mutation methods matching existing backend routes, build a chained-action command, resolve refs with `matchRef` (exact → unique prefix → unique substring → reject ambiguous), reuse `refreshAndRender`, and cover no-arg listing plus success/failure dispatch tests.
- Preserve existing public client method signatures when adding a project-scoped variant. If an old unscoped method is already consumed by interfaces or function values, keep it exact and add an explicit method such as `GetTaskForProject` or a private scoped helper for new callers; do not silently widen the old signature. Keep legacy task-detail rendering/parsing behavior unchanged while routing attachment-specific operations through the scoped API.
- When widening enum-like command keywords, keep backward-compatible synonyms normalized through one helper and parse optional trailing numeric arguments without breaking existing fixed-arity calls.
- When a backend default would mask invalid optional input, validate at the client boundary instead of silently omitting the field. For schedule creation, mirror the backend `repeat_interval` bounds of `1..365` for repeat schedules, return an error for `0`, negatives, or values above `365`, and test that invalid calls fail before HTTP while valid repeat intervals are posted explicitly.
- When two public client methods share a body that differs only by a path segment, extract a private helper that accepts the segment. Keep public signatures and call sites unchanged, and test each delegating function for path/query routing, success, and error propagation.
- Keep client regression tests compatible with the repository's declared Go toolchain. For form assertions, call `r.ParseForm()` and inspect `r.PostForm` directly when newer helpers such as `url.Values.Clone` are unavailable; do not let a test-only standard-library API choice obscure the transport behavior under test.
- For independent fetches, use `sync.WaitGroup` with each goroutine writing to its own result/error variable, then merge after `wg.Wait()`. Preserve mixed error semantics by keeping structurally distinct paths where needed, such as all-sections fan-out vs. single-section explicit fetch.
- For `--json` output, every marshaled struct must have explicit `json:` tags. Scraper-derived structs without tags marshal PascalCase field names and break `jq` pipelines. Add marshal tests that assert lowercase/snake_case keys.
- Preserve JSON collection shape for empty results: structured or HTML list parsers should return a non-nil empty slice, such as `make([]T, 0)`, so `json.Marshal` emits `[]` rather than `null`. Add focused CLI or serialization regression coverage for empty pages.

## Best-Effort Diagnostic Enrichment

- When a primary backend result remains useful without optional diagnostics, fetch the secondary source only after primary success. Keep the established primary renderer/table unchanged and treat secondary transport, decode, and empty-data failures as non-fatal.
- Gate optional enrichment before starting its request: if the caller's output does not display or otherwise consume it, such as list-only project loads during CLI setup, startup, or selection, fetch and decode only the primary collection. When enrichment is requested, preserve concurrent independent fetches and the established best-effort error semantics.
- For regressions that remove discarded I/O, use a deterministic `httptest` server with request counters and a delayed optional endpoint. Assert that list-only completion does not wait for the optional delay and makes zero optional requests; complement it with capacity-aware request-count, rendering, and failure tests plus no-project/unknown-reference cases to prove resolution and scoping remain unchanged.
- Verify the secondary payload against current backend handler or Swagger before coding. For analytics/capacity integrations, account for provider-level errors and alternate populated limit collections rather than assuming one provider or one limit field.
- Allowlist operational fields for terminal output, such as provider/account status, percentage used, reset time, and provider error. Do not render account-detail blobs, tokens, API keys, or other credentials. Keep diagnostic rows compact, deterministic, single-line, and plain text.
- When the secondary source is unavailable or has no usable account-limit data, append a helpful command hint, such as `/analytics usage`, rather than failing or implying provider health. Add tests for primary-only output, secondary failure, provider errors, multiple providers, and empty or alternate payload shapes; preserve existing JSON output contracts.

## Offline Startup And Recovery UX

- For TUIs that require the backend, use neutral initial status copy such as `Connecting to <server>` until a health check or required fetch succeeds. Do not show `Connected to <server>` before `checkConnection` or equivalent backend validation passes.
- Classify backend failures into authentication-required, transport/offline, and reachable-but-unhealthy categories. Non-authentication HTTP failures, malformed successful-response payloads, and other decode/API errors prove that the configured endpoint answered; they must not be presented as offline or accompanied by advice to start a server that already responded. Preserve `connected=false` for every failed health check, and clear the unhealthy classification on a later successful health check.
- Keep the classification at the client boundary with a reusable predicate such as `IsReachableError`, defined as non-authentication and non-transport failure. Model, header/status/hint, and backend-required CLI preload paths should consume that distinction through shared formatters rather than duplicating string checks. Authentication-required presentation remains higher priority than both reachable-error and offline presentation.
- A reachable-but-unhealthy diagnostic may include a safe HTTP status or decode/API error, but never response bodies, credentials, cookies, tokens, or other secret-bearing data. Keep the diagnostic concise and useful for debugging without implying that health succeeded.
- Preserve periodic health retry behavior across all categories. Repeated HTTP/decode failures remain unhealthy, connection refusal/timeouts retain existing offline recovery guidance, `401` and exact login redirects retain sign-in-required guidance, and health success is the only path that may render online.
- When the backend is unreachable, include concise recovery actions in terminal UI state and backend-required CLI stderr: start/check the local backend and set `-server` or `OPENVIBELY_SERVER_URL` when using a non-default backend.
- Distinguish authentication failures from transport/offline failures: a redirect or `401` means the backend is reachable but the session is missing or invalid, so do not render it as `offline` or give only server-url advice.
- For cookie-session login, classify request-construction and transport failures separately from credential rejection. Preserve a typed or equivalent transport error that contains neither submitted credentials nor response bodies, so the TUI can show offline recovery while keeping the masked login retry available; keep `401` or exact-path `/login` redirects generic and retryable as invalid credentials. Add client regressions for both classifications and secret redaction.
- At CLI entry points that support configured `-user`/`-pass` or environment credentials, dispatch static help and command-discovery aliases (`help`, `?`, `commands`, including a leading slash) before configured-login preflight so those paths remain backend-independent. If configured login fails with a typed transport error, delegate to the same shared offline-recovery formatter used by model and backend-required CLI paths; if an outer error needs context, wrap the typed cause without losing its classification. Preserve credential redaction, do not collapse transport failure into an invalid-credentials message or block static help, and keep successful configured-cookie flows unchanged.
- Never use a secret-bearing environment variable as a flag's default value when usage may call Go's `flag.PrintDefaults` or otherwise render flag defaults: the standard help output prints that default verbatim, so `OPENVIBELY_AUTH_PASSWORD=... openvibely-terminal --help` can leak the password. Keep secret flag defaults empty or redacted and resolve environment credentials after parsing (or redact custom usage), then regression-test `--help`/`-h` as well as `help`, `?`, and `commands` with a sentinel secret asserted absent while static help remains backend-independent.
- For interactive recovery, expose a safe sign-in/session recovery action in the command registry (or an equivalent in-terminal path) and keep credentials out of process arguments; do not make a cleartext `-pass` example the only documented recovery path.
- Keep `help` and other static command discovery paths backend-independent so users can recover without a running server.
- Do not add automatic install/start, hidden background services, or platform-specific bootstrap behavior while improving offline guidance. Setup, doctor, or bootstrap affordances should be explicit, backend-independent by default, and safe on macOS, Linux, and Windows.
- Add regression coverage for healthy startup status, unreachable-backend recovery guidance, reachable-but-unauthenticated recovery and sign-in guidance, reachable-but-unhealthy health HTTP/decode failures, project-load HTTP/decode failures in both TUI and CLI modes, offline help with configured credentials, configured-login transport failure, and nonzero backend-required CLI failure with human-readable recovery text plus transport details. Include a representative assertion that the model, CLI, and configured-login surfaces derive their full recovery text from the shared formatter rather than duplicated literals.

## Web UI Parity

1. Inventory actual navigation from `web/templates/layout/sidebar.templ`, route registration, handlers, templates, and sub-screens.
2. Cross-check each visible feature against Swagger and handler source.
3. Classify each feature as native JSON, HTML/HTMX parsing, or blocked pending backend support.
4. For attachment parity, audit task-detail file management and chat multipart attachments as separate workflows. Verify the backend/web route, method, fields, client request encoding, shared input or CLI syntax, terminal rendering, and mutation coverage; a read-only task-attachment tab or a text-only `message` request does not establish support for uploading, deleting, or sending attachments.
5. Preserve feature parity without copying web navigation chrome.
6. Do not promote API-only concepts into top-level resources unless current navigation proves they are parity targets.
7. Account for tasks and task details, thread, changes, schedules, chaining, attachments, lifecycle, grades, pulse, reflection, alerts, skills, agents, models, workers, channels, personality, automations, insights, and analytics.

## Repository Boundary

- Keep client code dependent only on backend behavior that already exists when backend changes are out of scope. Missing machine-readable support is a parity constraint, not permission to add backend endpoints.
- Before resuming interrupted work, re-read the latest scope and inspect repository state in every in-scope repository. If a directory is not a Git worktree, report that fact rather than assuming it is clean.
- Run backend validation only when backend edits are in scope.

## Validation And Delivery

- Avoid broad filesystem operations that can traverse linked worktrees or modify unrelated files.
- Preserve endpoint, HTML parser, command-dispatch, and terminal-rendering coverage according to the changed feature group.
- When adding focused regressions to existing test files, keep the change additive and confirm neighboring pre-existing tests and contracts were not accidentally replaced or deleted.
- Use a freshly built shipped binary when source changes affect runtime behavior.
- When a backend is already running, smoke-test representative read-only CLI commands, explicit project selection, ambiguity, and unknown-command exit paths.
- For a transport-focused Go client change, finish with `go build ./...`, `go vet ./...`, `go test ./... -count=1`, `gofmt -l`, and `git diff --check` after running the focused regression tests; treat any output from `gofmt -l` or `git diff --check` as a failure to resolve. Add the narrowest relevant `go test -race` package or test invocation only when the diff changes concurrent transport behavior, goroutine ownership, cancellation, or shared mutable state, or when the task explicitly requires it. Do not use a repository-wide race run as a routine completion gate.
- For large parity work, land and validate one feature group at a time.
