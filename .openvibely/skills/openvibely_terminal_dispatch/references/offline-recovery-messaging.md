# Offline Recovery Messaging

Use this reference when changing connection-failure wording or error propagation across the TUI, headless CLI, or `cmd/openvibely-terminal` startup paths.

## Centralization Pattern

- Keep one shared formatter, `internal/terminal.OfflineRecoveryMessage(baseURL, err)`, for transport failures that mean the backend cannot be reached. It should provide the backend URL, `/status` recovery guidance, `-server <url>` / `OPENVIBELY_SERVER_URL` configuration guidance, and optional diagnostic details.
- Route all applicable transport-error presentation through that formatter: interactive model transitions, generic command/project-load failures, headless CLI project loading, and configured-credential startup login failures. Do not duplicate the heading or recovery instructions in callers.
- Preserve error classification while changing presentation. If a caller wraps a configured-login transport error with a user-facing recovery message, implement `Unwrap` so `client.IsLoginTransportError` and other `errors.Is`/`errors.As` checks still work.
- Keep credential rejection separate from transport failure. Invalid credentials should remain generic, retryable, and redacted; transport diagnostics must not include submitted credentials or response bodies. Successful login and empty configured credentials must retain their existing behavior.
- Keep the shared formatter's `baseURL` and optional error detail explicit. Test both the common guidance and detail inclusion, and ensure no caller accidentally exposes a secret through `err.Error()`.

## Terminal-Safe Connection Diagnostics

- Treat all connection error text as untrusted, including `url.Error`/`net.OpError` strings generated by Go's transport stack and backend HTTP/decode error messages. They can contain the request URL, userinfo, query/fragment tokens, response-derived text, ANSI/OSC controls, and injected line breaks.
- Route optional formatter details and the model's stored connection detail through one helper that first removes terminal controls and flattens to one line, redacts every embedded HTTP(S) URL with the same safe URL display policy (drop userinfo, query, and fragment), masks common key/value credential fields such as `token`, `password`, `authorization`, `cookie`, and `api_key`, then bounds the final detail by display width.
- Sanitize when assigning `connErr`, not only when composing recovery copy. Defend again at every `/status` error row so manually seeded, legacy, or future state cannot bypass terminal safety.
- Keep the diagnostic useful: retain safe operation/status/transport context, distinguish offline from reachable-unhealthy guidance, and do not replace the full error with an opaque generic message merely to redact it.
- Add focused regressions with a realistic wrapped transport error containing URL userinfo, query, fragment, newline, and terminal escape data, plus a reachable HTTP/decode error containing a credential assignment, controls, and oversized backend text. Assert both recovery formatters and both `/status` branches disclose no secret or control data, render one bounded detail line, and retain expected safe context.

## Backend-Independent Setup Recovery

- Provide a registered `setup` command for static recovery guidance, exposed consistently as interactive `/setup` and one-shot `openvibely-terminal setup`. Mark it backend-independent and non-project-scoped so dispatch and CLI preflight make no HTTP, authentication, project, or mutation request before rendering it.
- Render the backend installation documentation as static terminal-native instructions. Select distinct macOS/Linux and Windows guidance at runtime; include source-checkout startup (`./start.sh` when documented), server health verification with `/status`, and remote endpoint configuration through `-server <url>` or `OPENVIBELY_SERVER_URL`.
- State the safety boundary in output and documentation: setup only explains the workflow. It must never install or clone software, start a process, change configuration or files, authenticate, or otherwise modify machine/backend state.
- Surface the command in generated help, first-launch/offline recovery, status views, and README. Keep README wording and terminal instructions in parity without implying automatic setup.
- For an unreachable explicitly configured remote URL, place checking/correcting that URL before local-install or local-start instructions, while still retaining a discoverable setup path. Sanitize/redact displayed configured server URLs so userinfo and other unsafe fragments are not emitted.

## Reachable But Unhealthy Backend

- Preserve reachability separately from health. Connection refusal, DNS/TLS failures, and timeouts mean the backend cannot be reached; an HTTP response such as `5xx`, or a malformed/invalid health payload from a responding server, means the backend was reached but is unhealthy or unusable.
- Do not route every non-nil health error through offline wording such as "start the backend." Carry a typed or equivalent client-side distinction into TUI startup, project loading, status rendering, and backend-required CLI errors so reachable-server guidance can point users to diagnosis without implying that the process is absent.
- Keep authentication-required responses as their own higher-priority state: `401` or the exact login redirect means the server is reachable but the session needs recovery, not that the backend is unhealthy or offline.
- Add focused regressions for transport refusal, HTTP `500`, malformed health data, and authentication failure across the visible health/recovery paths. Assert distinct labels and guidance, preserve useful error details, and verify that offline/bootstrap and sign-in behavior remains unchanged.

## Regression And Audit Checks

- Cover setup with platform-output, help discovery, CLI preflight/no-request, no-project, terminal-safety/redaction, remote priority, offline, auth-required, reachable-unhealthy, and README-parity tests. A rejecting test server is useful proof that setup itself sends no request.
- After implementation or fixes, run `go build ./...`, `go vet ./...`, `go test ./... -count=1`, and `git diff --check` from the active task worktree. Add focused race-detector coverage only when the fix changes asynchronous health, authentication, or model-state transitions.
- During the separate fresh audit-only pass, inspect callers, wrapping, redaction, synchronization with `main`, conflict markers, and worktree cleanliness using read-only commands only. Do not rerun build, test, format, or other modifying commands in that audit pass; report validation previously run separately.
