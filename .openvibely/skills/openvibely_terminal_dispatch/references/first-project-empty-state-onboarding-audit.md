# First-Project Empty-State Onboarding Audit

Use this reference when auditing startup, project-list, or empty-state behavior against product vision.

A zero-project account is a first-run workflow, not merely an empty collection. Verify that startup and the project-list view offer a discoverable path to create the first project, and that the ordinary chat/input hint does not tell the user to select a project when no project exists. The empty state should explain the next action in product language while preserving the technical command path needed for implementation.

Treat project-list loading as a separate state from confirmed emptiness. A newly constructed model commonly has a nil or zero-length project slice before the asynchronous list request returns; do not use `len(projects) == 0` alone to show first-project creation guidance or to reject plain-text input. Add an explicit loaded/settled signal, or equivalent response provenance, and gate zero-project onboarding on a successful completed list response with no projects. Reset that readiness signal whenever a new project-list request begins, including a deferred `/project` selection or refresh; set it only after the list response is accepted or a successful creation installs a known project. Tests that populate `m.projects` directly must also set the readiness flag when they intend a confirmed list; leaving it false should model an in-flight load. During initial loading, retain connecting/loading guidance and do not imply that the account is empty. Add a regression where health completes and input/rendering are observed before a delayed non-empty project response, then verify that creation guidance never appears and that the eventual projects-exist-but-unselected behavior still points to `/project \u003cname\u003e`.

Inspect the project-loading path in `internal/terminal/model.go`, empty-state and hint rendering in `internal/terminal/view.go`, and project/create command registration in `internal/terminal/registry.go`. Check both interactive startup and one-shot CLI behavior: no-project loading should fail safely for project-scoped commands, while the interactive empty state should expose an actionable creation route or equivalent guidance only after the empty response is confirmed. Add focused regressions for zero projects, first-project creation guidance, the loading boundary, and the normal selected-project hint so the fix does not regress established project selection behavior.

Keep the output surfaces intentionally distinct. Prefer one canonical creation-command string or helper for the startup transcript, empty `/projects` and `/project` rendering, online input hint, and plain-text no-project response. When the project list is confirmed empty, plain text should explain how to create a project; when projects exist but `selectedID` is empty, retain `/project \u003cname\u003e` selection guidance. Preserve the project-independent create route and verify that interactive creation selects the new project.

Do not mix human onboarding text into machine-readable CLI output. Keep `--json projects list` on its existing direct JSON path and collection shape, including `[]` for an empty list; test that the output parses as JSON and contains no creation prose. Exercise the real slash-command dispatch paths for both empty project commands, then run the focused tests and repository checks (`go build ./...`, `go vet ./...`, and `go test ./...`).
