# Command-Surface Documentation Parity

Use this reference when a TUI/CLI command already works but its README or help surface is incomplete or inconsistent.

- Treat the registered action set and rendered `help \u003ccommand\u003e` output as the source of truth. Inspect the command registry, help renderer, CLI flag parsing, and dispatch tests before editing documentation; do not invent actions or change request/confirmation behavior merely to make docs match.
- Keep the README command table, detailed command section, and `help \u003ccommand\u003e` output aligned. For each supported action, document the same spelling and operand shape, and include one valid interactive example plus one valid one-shot CLI example.
- Store concrete examples in the command registry's help metadata and have focused consistency coverage derive expected help and README checks from that list. Include the default/list form and each documented lifecycle or destructive form; otherwise a help block can look plausible while still hiding a supported action.
- Verify examples against the actual parser. In particular, place global CLI flags such as `--force` where `RunCLI` parses them, normally before the command, and state the mode-specific destructive behavior: interactive removal confirms with `yes`, while one-shot CLI removal requires `--force`.
- Preserve adjacent behavioral guidance while documenting the surface, including project-selection requirements, aliases, browser-only OAuth connection/callback flows, and existing selector/confirmation semantics. Prefer help metadata or a narrow focused regression over duplicating action literals in dispatch code.
- For documentation-only changes, inspect the parent-to-current diff or equivalent source comparison to confirm dispatch, reference resolution, project scoping, refresh, and confirmation code did not change. Do not infer unchanged runtime behavior from the README alone.
- If recorded or direct command output contradicts inspected source, verify the producer's execution context before treating it as a source defect: compare `pwd`, `git rev-parse --show-toplevel`, `git rev-parse HEAD`, `git status --short --branch`, the task worktree and parent checkout, and any `go.work`/`go.mod` module boundary and local entrypoint imports. Output from another checkout can look like stale source while the active task checkout is correct. During a strictly read-only audit, do not rerun `go run`, builds, tests, or formatting just to reconcile the discrepancy when they may update caches or files; use read-only checkout/source comparison and recorded validation evidence, and report any unresolved contradiction instead of declaring the audit clean.
- Validate the documentation/metadata change with a focused help test, `go build ./...`, `go test ./...`, `go vet ./...`, a direct `go run ./cmd/openvibely-terminal help \u003ccommand\u003e` inspection, and `git diff --check`. Review the final diff/status to ensure only intended documentation/help/test paths changed.
