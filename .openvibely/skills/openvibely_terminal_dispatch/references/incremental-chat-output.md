# Incremental Chat Output In The TUI

Use this reference when changing `internal/terminal` chat submission, transcript rendering, status polling, reconnect behavior, authentication invalidation, login, or active-project transitions.

- Keep one mutable assistant transcript entry for an active turn. Apply output chunks or verified partial status output to that entry, then reconcile it once with the authoritative terminal status so plain output and JSON output contain one final assistant response rather than a chunk history or duplicate completion.
- Treat the dedicated per-execution stream as an acceleration and display path, not the terminal authority. Polling must continue through stream disconnects and terminal frames; `done` and `error` should re-fetch status immediately, and only a verified terminal status may clear pending/busy state.
- For a direct execution, open the stream as soon as the execution ID is known. For a queued submission, wait until status polling authoritatively promotes the accepted queue/message ID to an execution ID. Preserve both identities for correlation and reject unrelated or unverified completion events.
- Maintain the incorporated output length as a UTF-8 byte offset. On disconnect, preserve visible partial output, use processing-status partial output only as a truthful fallback, and reconnect from the latest exact byte offset. Do not reset the transcript or append the same replayed bytes twice.
- Flush queued cadence output at every state boundary that invalidates stream ownership or resets stream storage. In particular, flush before `beginLogin` advances the session generation or invalidates the chat stream, and before a changed-project `setActiveProject` advances the project generation, invalidates the stream, clears old pending identity, or resets output. Preserve accepted pending chat through login recovery, but retain the existing behavior that project changes clear old-project pending state and same-ID project updates do not trigger a flush/reset transition.
- Treat transcript append boundaries as ordering barriers even when they do not invalidate stream ownership. Before appending the rejection for an overlapping plain-text submission, flush accepted queued assistant bytes so the warning cannot overtake the first assistant block. Keep the active turn pending and do not issue a second send.
- When `/events` is visible, validate a `chat_response_done` event against the pending execution and project before rendering its event entry. For a matching completion, flush queued assistant bytes first, then append the visible event and perform authoritative completion/reconciliation. Do not force a redraw for malformed, unrelated, or foreign completion events; preserve their existing display and settlement behavior and the normal cadence for ordinary events.
- Interactive slash submission appends the user command before its handler runs unless explicitly ordered otherwise. Flush queued assistant output before recording the slash command so transcript order remains assistant bytes, user command, then transition/result message. Keep defensive flushes inside login/project invalidation helpers as well because those helpers have non-interactive callers. `flushChatStreamOutput` must remain idempotent so layered safeguards render the mutable assistant entry exactly once.
- Flush queued cadence output at the shared authentication-invalidation boundary before advancing session or chat-stream generations, clearing pending chat state, or invalidating stream ownership. Do not protect only the direct stream-disconnect branch: health checks, status-count refreshes, project loads, generic command results, and future callers can all trigger the same auth transition. Keep caller freshness guards intact, centralize the ordering in `markAuthRequired`, and avoid caller-specific auth flushes.
- Guard every stream chunk, terminal frame, status response, reconnect command, and cleanup message with the owning project/session, submission/generation, and execution identity. Reject stale or foreign messages before they mutate transcript, pending chat, busy state, polling, or stream ownership. Preserve serialized submission behavior by reserving the active turn before the POST.
- Cancel and close the per-execution stream on completed, failed, cancelled, or locally aborted turns, project changes, login/session invalidation, and model shutdown. Make terminal handling idempotent so duplicate `done`/`error` frames cannot append, poll, or clean up a later turn.
- Add focused regressions through the real interactive command path for manual `/login` and changed-project `/project` transitions. Assert exact UTF-8 bytes render once in order before the user command and system transition message; also assert queued-render clearing, stream/project generation advancement, accepted-chat retention for login, and old-project pending-chat clearing for project switches.
- Add ordering regressions for a buffered first assistant block followed by both a rejected overlapping plain submission and a matching visible `chat_response_done`. Assert log role/text order, one final assistant entry, authoritative replacement of partial output, queued-render clearing, and preservation or settlement of pending state as appropriate.
- Regression coverage should also exercise incremental chunks, authoritative completion and failure, stale stream messages, queue promotion, disconnected recovery with UTF-8 output, status fallback, cancellation, and exactly-once plain/JSON final rendering. For auth invalidation, include representative non-stream sources such as health and status-count messages; assert queued assistant bytes render before auth-recovery text, the queued-render flag clears, and stream ownership advances. Run focused changed-path race tests when concurrency is involved; if the repository-wide race suite exposes an unrelated pre-existing race, isolate and report it rather than changing unrelated code.
