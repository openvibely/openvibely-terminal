# Selective Bulk Alert Actions

Use this guidance when implementing or auditing `/alerts read-bulk <id|title>...` or `/alerts delete-bulk <id|title>...`.

- Resolve every supplied reference against the selected project's complete, pagination-aware alert collection before beginning a mutation. Use the existing alert-specific resolver so exact ID/title precedence, ambiguity, missing-reference errors, and safe display handling match single-alert actions.
- Build the request from resolved stable IDs, reject a repeated resolved ID locally even when two different references name it, and make no request for ambiguous, missing, duplicate, or foreign-project references. Do not rely on backend atomic rejection as the only UI safety check.
- Send the selected `project_id` and JSON `{ "ids": [...] }` with `Content-Type: application/json`. `POST /alerts/read-bulk` returns `{ "updated": n }`; `DELETE /alerts/bulk` returns `{ "deleted": n }`. Decode and report the backend count rather than assuming the input length.
- Treat `updated` or `deleted` as a required response value, not a Go `int` that defaults absent or `null` JSON fields to zero. Decode with presence-sensitive representation, then reject absent, `null`, or negative counts before returning a result. Explicit `0` is valid. A 2xx error-object body or any body without the endpoint's required count is malformed, not a zero-result success.
- Keep this validation at the client boundary, before terminal success rendering. A malformed counted response must produce no plain success status and no list refresh; in `--json` mode it must produce no success count payload. Preserve valid positive and explicit-zero behavior.
- `read-bulk` is non-destructive. Treat `delete-bulk` as destructive: resolve and capture the selected IDs before presenting the existing interactive `yes` confirmation. In headless CLI mode, require `--force`; resolve first so invalid references fail before a force/confirmation error and never mutate.
- The interactive delete confirmation must identify every captured resolved target, not merely its count. Render a terminal-safe canonical label for each alert, normally sanitized `"title" (id)` with the stable ID retained even when a title is absent or duplicated. Build this text from the captured resolved records, never from the original input or a later catalog lookup.
- Regression coverage for interactive delete should resolve partial and/or title references, assert the displayed canonical target identities, then change the mocked catalog before `yes` and assert the mutation still submits exactly the IDs shown in the confirmation. Also retain cancel coverage proving no mutation occurs.
- Refresh and render the selected project's alert list only after a successful bulk mutation. A backend failure must show the error without success output or a refresh. Preserve the established whole-list `/alerts read-all` and `/alerts clear` paths unchanged.
- Preserve stable machine output: in `--json` mode, emit the backend-shaped counted result (`updated` or `deleted`) rather than a refreshed rendered list.
- Cover direct-client and terminal dispatch/CLI JSON behavior for both read and delete. Each count endpoint needs explicit zero and positive success cases, plus missing, `null`, negative, and 2xx error-object count bodies. For every malformed case, assert an error, no plain success/refresh, and no JSON count output.
- Also cover a partial selection that leaves other alerts untouched, later-page title resolution, duplicate and foreign/missing rejection before HTTP, request method/path/project/payload shape, returned count, failure-without-refresh, interactive confirm/cancel, CLI `--force`, JSON result, and unchanged whole-list actions.
- Bubble Tea dispatch tests may stop after the first asynchronous command is returned. For a command that resolves the alert collection and schedules the mutation as its follow-up `tea.Cmd`, use a narrow test helper that executes that next command; do not distort production dispatch merely to fit a single-step test harness.

Run `gofmt` on changed Go files, focused client and `internal/terminal` regressions, then `go build ./...`, `go vet ./...`, `go test ./... -count=1`, and `git diff --check`.
