# Terminal Model Provider Editing

Use this reference when adding, changing, or auditing `models edit <model>` in `openvibely-terminal`. Load `openvibely_backend_client` and `terminal-model-provider-setup.md` as well: edit must share the existing model command surfaces and secret safeguards rather than introducing a second provider setup path.

- Implement one shared edit flow for interactive slash dispatch and one-shot CLI: resolve the model reference with `matchRef` (exact, unique prefix, unique substring, ambiguity rejection), fetch authoritative edit details, merge only explicit user options, submit the backend update contract, then refresh via the established list/render path.
- Keep configuration name and model ID as separate reference candidates. Do not concatenate them into `matchRef`'s one `name` callback: that destroys exact-configuration-name precedence when another item contains the same name plus a different model. Resolve canonical IDs and exact configuration names first; consider an alternate model-ID match only as a lower-priority fallback, preserving ambiguity errors at every tier. Regress an exact configuration name that collides with another configuration's combined name/model text.
- Do not construct an update from the rendered model list card. The authoritative detail read owns credentials and provider-specific state that must survive a partial edit. Keep secret-bearing fields in private, non-rendered, non-JSON-marshaled client representation; merge requested values while retaining all unspecified credentials, auth fields, provider settings, and reset-sensitive fields.
- Treat the edit route as a full browser-form replacement, not a patch. Mirror every detail field whose missing form value the handler resets, including OpenAI-compatible `default_max_tokens`; preserve and resubmit it even when the terminal has no option to change it. Add a handler-contract regression that starts with a nonzero value and proves an unrelated edit retains it.
- Support explicit edits to name, model selection, default state, worker settings, and local/OpenAI-compatible endpoint only after applying current backend validation. Inspect normalization as well as rejection paths: if the backend converts an unsupported OpenAI model ID to a fallback/default, reject that requested value locally before the update rather than reporting success for a different persisted model. Keep accepted-ID validation synchronized with the backend and regress zero update requests for an unsupported value.
- API-key replacement is deliberate: interactive mode must use the existing masked secret prompt, while one-shot use must read through the existing stdin-only secret option. Never accept a key as an ordinary command operand or display it in transcript, history, help defaults, errors, logs, plain output, or JSON. Apply the malformed-command fallback redaction rules from `terminal-model-provider-setup.md` to `models edit` sensitive options as well as `models add`.
- Preserve backend provider/auth reset and OAuth semantics. A completed update does not establish an OAuth connection by itself; render connected only when the backend-confirmed status says so. Authentication-required errors after save or during status handling take precedence over generic successful-save or unknown-status fallbacks.
- After a successful update, attempt the normal model refresh. An ordinary refresh failure is best effort and must retain the confirmed save result. An authentication-required refresh failure must instead surface sign-in-required guidance and must not claim successful connected/refresh state.
- Treat configuration names as untrusted single-line terminal metadata. Validate or sanitize control characters before mutation, and independently sanitize server-returned detail/card names before composing statuses such as `updated <name>`. Regress raw TUI transcript and plain CLI output for ANSI, newline, carriage return, and other control injection; assertions must run before ANSI-stripping helpers.
- Register and document the action consistently in command dispatch/registry, CLI parser and project preflight, slash completion, command help, README, user guide, and the rendered model-list hint in `view.go`. Keep existing list, filter, default, delete, capacity, and project behavior unchanged.

Focused regressions should cover authoritative read-modify-write form fields, preservation of unedited provider/credential fields and nonzero `default_max_tokens`, API-key retention and replacement redaction, malformed sensitive input, ambiguous references, exact-name versus alternate-model reference collisions, unsupported model selection rejected before update, invalid local/backend validation with no success, compatible-endpoint serialization, backend-confirmed pending OAuth status, success despite ordinary refresh failure, auth-required refresh failure, raw terminal-safe success labels in TUI and CLI, interactive/CLI parity, JSON redaction, rendered edit hint, and existing model actions.
