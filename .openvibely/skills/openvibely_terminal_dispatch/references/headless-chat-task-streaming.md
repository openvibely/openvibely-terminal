# Headless CLI Chat And Task Streaming

Use this reference when changing one-shot/headless `chat <message>` or `tasks reply` (including compatible aliases) in `RunCLI` or the CLI dispatcher. Keep this path separate from Bubble Tea's interactive transcript and stream ownership.

## Execution Flow

- Submit through the existing authenticated client and retain the accepted identifier. It may already be an execution ID or may be a queued thread-input/message ID; do not assume the first ID is streamable or remains stable.
- Keep polling the accepted ID until status/promotion evidence supplies a verified execution ID. Preserve an alias from the accepted ID to the promoted ID so status, terminal events, and cleanup continue to correlate. Apply the selected `project_id` to task-follow-up submission, status/live-event filtering, and any project-scoped request; never accept a foreign non-empty project event.
- Task-thread acknowledgements are not uniformly streamable: a successful swarm-parent follow-up may return the backend's `TaskThreadQueuedFollowupResponse` without `data-exec-id` or `data-thread-input-id` because orchestration is scheduled internally. Do not treat that intentional no-identity success as an empty-ack transport failure after the mutation has already succeeded, and do not invite a duplicate retry. If a supported authoritative task/status recovery path exists, use it; otherwise report an explicit accepted/non-streamable outcome rather than claiming streamed completion. When both identities are absent and no recovery path is supported, do not issue speculative status or `/events/chat` requests: emit one plain confirmation or one `accepted` NDJSON record and return success. Add a regression for the swarm-parent response alongside direct and queued ordinary follow-ups.
- Once an execution ID is authoritative, consume `GET /events/chat/<exec_id>?offset=N`. Use the exact UTF-8 byte length already rendered as `offset`, parse unnamed data chunks plus named `done`/`error` frames, and reconnect after recoverable disconnects from the latest offset with bounded backoff. Clean EOF alone is not completion; polling remains the terminal authority.
- Treat a named `done` or `error` frame as a signal to reconcile, not as the final result. Fetch the authoritative chat/execution status before deciding success, failure, final output, or task IDs; do not return directly from the stream frame or trust its text as the complete response. Keep this reconciliation idempotent so duplicate terminal frames cannot append or settle twice.
- Make terminal handling idempotent. Preserve already-flushed partial output, avoid replaying bytes after reconnect, and ensure a late or duplicate frame cannot settle a newer command or append a second final response.
- For queued task follow-ups, the multiplexed `/events/live` promotion event is not a replayable identity source. If the stream closes or the event is missed, recover the execution identity through an authoritative/replayable status or task-specific path supported by the backend contract; do not wait indefinitely on a one-shot event stream or assume reconnect will replay it. If no identity can be recovered within the bounded command lifetime, fail clearly rather than reporting success. The no-identity swarm-parent acknowledgement is a separate successful accepted outcome and must not be conflated with lost promotion.

## Output And Cancellation

- Write plain-text deltas immediately rather than buffering until the final status. Preserve the established non-empty response trailing newline at terminal completion.
- In `--json` mode, emit stable valid NDJSON records for each delta and the terminal outcome using explicit JSON tags. Keep JSON framing separate from plain rendering and return the established nonzero exit result after a failed execution even when partial output was emitted.
- Propagate the caller-owned CLI context through submission, status polling, stream reads, reconnect waits, and project preload. Ctrl-C/cancellation must close the active HTTP request promptly, avoid a false success/error record, and not strand a reader goroutine or reconnect loop.
- Distinguish caller cancellation from an internal deadline or bounded reconnect/promotion failure. A user cancellation may terminate quietly according to the CLI contract; command timeout, lost promotion identity, and reconnect exhaustion must return a nonzero, actionable error and must never be converted to `nil` success merely because partial output was already written.

## Tests And Validation

- Add deterministic coverage for output before completion, multiline/Unicode chunks and byte offsets, done/error/cancelled outcomes with authoritative status reconciliation, partial-output failure, queued-ID promotion for chat and task follow-up including a missed/disconnected live stream, foreign-project filtering, disconnect/reconnect without duplication, request cancellation versus deadline timeout, and plain/NDJSON serialization.
- Add a task-follow-up contract regression for a successful swarm-parent response with no execution or queue identity; assert exactly one successful submission, no false empty-ack failure, no silent retry or speculative status/stream request, and the documented accepted/no-stream plain and JSON behavior.
- Keep non-streaming list/show commands and interactive rendering regression-covered and unchanged. Run focused tests, then `go build ./...`, `go vet ./...`, `go test ./... -count=1`, `gofmt -l cmd internal`, and `git diff --check`. Because streaming changes are concurrency-sensitive, run the narrowest relevant chat/stream packages or tests under `-race`; expand to `./...` only if the behavior crosses package boundaries or the task explicitly requires it.
