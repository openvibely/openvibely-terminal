# Terminal Model Provider Setup

Use this reference when adding, changing, or auditing terminal model-provider configuration in `openvibely-terminal`. Load `openvibely_backend_client` as well to verify the current backend route and create-form fields before implementation.

- Expose one shared `models add` action through interactive dispatch, one-shot CLI parsing, slash completion, static help, README, and user-guide examples. Do not create diverging TUI and CLI mutation paths.
- Submit the backend-owned form contract through a client-layer `POST /models` method. API-key providers require the server-defined name/provider/model/auth fields and key; local Ollama uses `provider=ollama`, name/model, and an optional validated base URL. Never duplicate normalization or claim client-side validation is authoritative.
- Read API keys only from masked interactive input or an explicit stdin-only CLI option such as `--api-key-stdin`. Reject character-device stdin so terminal echo cannot reveal a key; accept only piped or redirected input. Do not accept secrets in command arguments, flags, environment-backed help defaults, history, logs, transcript, rendered output, errors, or JSON.
- Treat every error surface as secret-bearing: redact a submitted key even if the backend reflects it, and ensure unsupported-option or parse errors cannot echo a following secret. Redaction must fail closed: command submission records its display/history representation before reporting tokenizer errors, so an unmatched quote must use a conservative `/models add` sensitive-option fallback rather than return the raw command. Reuse the same sensitive-option classification for ordinary tokenized redaction and fallback detection; the fallback may replace the whole command with a generic redacted label once it establishes the models-add prefix and a sensitive option. Treat a stdin-only credential switch, including `--api-key-stdin`, as sensitive for command-display redaction too: although valid CLI use consumes no argv value, an accidental following pasted value must not enter interactive transcript/history. In tokenized redaction, distinguish a non-empty inline assignment from an empty one: `--api-key-stdin=value` redacts its right-hand side, but `--api-key-stdin= value` has no inline value and must redact the following token as well. Apply this rule to every sensitive option, including `--api-key= value`; `strings.Cut` reporting that `=` exists is not proof a sensitive value was consumed. The quote-aware tokenizer preserves balanced `""` and `''` as explicit empty tokens: when such a token immediately follows a sensitive option, it is an invalid empty operand, not proof that the following pasted token is safe to display. Redact that empty token and one additional following token conservatively before parser rejection, including credential-bearing endpoint input. In interactive mode, parse any non-wizard `models add` arguments before returning masked-prompt guidance so these malformed sensitive forms receive a local validation error with no request. Do not use a quote-preserving whitespace split as the fallback detector: malformed input can quote the option marker itself (for example, `"--api-key" "secret`), causing literal quote bytes to evade option matching. Normalize quote delimiters from the entire option-name portion before comparing it with the sensitive-option allowlist, not merely from its edges: both trailing quote-injected marker names such as `--api-key"=secret`, `--api-key'=secret`, `--api-key-stdin"=secret`, and `--api-key-stdin'=secret`, and internal quote injection such as `--api"-key=secret`, `--api'-key=secret`, `--api"-key-stdin=secret`, and `--api'-key-stdin=secret` must select the generic redaction fallback. Favor redacting the entire model-add command whenever malformed syntax makes precise value handling uncertain. Normalize the command root independently of quote/slash order: strip optional quote delimiters before and after removing the leading slash, so malformed input with quotes around the command name (`/"models"` or `/'models'`) and quotes around the complete slash root (`"/models"` or `'/models'`) both select the conservative fallback. The tokenizer and dispatch may consume more than one leading slash: a malformed `//models` root can still resolve as `models` after each layer removes a slash. Therefore fallback classification must remove all repeated leading slash delimiters, as well as quote delimiters throughout the root, before comparing it to `models` or `model`; otherwise malformed `//models ... --api-key "secret` reaches view, transcript, and history unredacted. The tokenizer also permits balanced quote fragments within a root, so root classification must remove quote delimiter characters throughout the normalized root rather than trimming edges only; `"/m"odels` and `'/m'odels` must classify as `models` when a later unmatched credential quote triggers the fallback. Mirror the tokenizer's leading-slash normalization before using whitespace fields: it removes one leading slash, then trims newly adjacent whitespace before parsing the root. Consequently `/ "models" add ... --api-key "secret` and `/ 'models' add ... --api-key 'secret` have a valid balanced `models` root despite a later unmatched credential quote; fallback classification must not treat the standalone `/` as the root or return the raw secret-bearing command. Command-vs-chat classification runs before fallback redaction and must use tokenizer-compatible root normalization rather than a short literal-prefix allowlist. In particular, leading empty balanced fragments such as `""/models` and `''/models` tokenize to `/models`; they must be dispatched as commands so a later unmatched credential quote reaches the redacted parse-error path, never chat/history/transcript or a chat request. Reject endpoints containing user info, query strings, or fragments, and redact inline endpoint values before they reach interactive history or transcript output.
- Validate provider-specific option combinations and required values before requests. Malformed endpoints and unsupported options must not POST, claim success, or refresh the view. Map authentication failures to sign-in guidance, with no refresh or connection claim.
- For OAuth-backed providers, create the backend configuration then present only the backend-provided authorization handoff/status. Do not report that the provider is connected until the backend confirms it. A successful create followed by a failed model-list refresh must still return explicit OAuth-authorization-required guidance and a safe browser handoff when the created model ID is known; otherwise direct the user to the backend Models page to initiate and confirm authorization. Do not degrade that path to a generic `added <name>` result.
- Classify post-create failures before applying the nonfatal refresh fallback. In particular, if either the refreshed model list or the OAuth-status lookup returns a typed authentication-required error after `POST /models` succeeds, propagate sign-in-required guidance rather than reporting `added <name>`, `oauth_status: "unknown"`, a browser handoff, or any connection/success claim. Only ordinary refresh/status failures may retain the successful-create result; OAuth fallbacks must say that status is unknown without inventing backend confirmation.
- After a successful creation only, refresh the visible model list through the shared list/render path so normal default selection immediately works. For non-OAuth configurations, a refresh failure may retain the successful add status; for OAuth, preserve the guidance above while accurately reporting that the refreshed list is unavailable.
- Add focused tests for API-key and Ollama request fields, masked/stdin credential handling, terminal-stdin rejection, redaction in plain and JSON output, malformed endpoints, unsupported options, backend validation, authentication failure, OAuth handoff/status, successful refresh, and default-selection compatibility. Test malformed-quote `/models add` lines both with a conventional `--api-key "secret` spelling and with quoted sensitive option markers such as `"--api-key" "secret`, trailing quote-injected marker names such as `--api-key"=secret`, `--api-key'=secret`, `--api-key-stdin"=secret`, and `--api-key-stdin'=secret`, internal-quote variants such as `--api"-key=secret`, `--api'-key=secret`, `--api"-key-stdin=secret`, and `--api'-key-stdin=secret`, and quoted command roots such as `/"models" add ... --api-key "secret`, `/'models' add ... --api-key 'secret`, `"/models" add ... --api-key "secret`, `'/models' add ... --api-key 'secret`, `"/m"odels add ... --api-key "secret`, and `'/m'odels add ... --api-key 'secret`. Include `/ "models" add ... --api-key "secret` and `/ 'models' add ... --api-key 'secret`: the initial standalone slash must receive the same normalization as the interactive tokenizer before fallback root matching. Include a `//models add ... --api-key "secret` case, because dispatch may normalize repeated leading slashes while the malformed-token fallback uses whitespace fields. Include leading-empty-fragment roots `""/models` and `''/models`, which require command-input classification to agree with tokenizer root parsing. Each malformed case must preserve its local parse/usage error, make no request, and prove the raw key is absent from rendered `View`, transcript, and every history entry. Also test `--api-key-stdin pasted-secret` in normal and unmatched-quote interactive input: each case must preserve its local parse/usage error as applicable, make no request, and prove the raw key is absent from rendered `View`, transcript, and every history entry. Add equivalent empty-assignment cases such as `--api-key-stdin= pasted-secret` and `--api-key= pasted-secret`; assert the following token is redacted before validation, no request occurs, and it is absent from raw view, transcript, and all history entries. Add empty double- and single-quoted operand cases such as `--api-key-stdin "" pasted-secret`, `--api-key '' pasted-secret`, and `--endpoint "" http://user:pasted-secret@host`; assert parser rejection, zero requests, and absence of the secret from the view, transcript, and every history entry. Add an OAuth-create-success/list-refresh-failure regression for plain and JSON outputs; it must retain authorization-required handoff/status guidance without claiming a connection. Also cover typed `401`/login-redirect failures after a successful OAuth create for both the list-refresh and status-lookup branches: they must surface sign-in-required failure without outputting a successful add or authorization handoff.
