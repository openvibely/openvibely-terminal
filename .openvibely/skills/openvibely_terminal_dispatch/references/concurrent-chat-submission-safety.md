# Concurrent Chat Submission Safety

Use this reference when auditing or changing chat submission, acknowledgement, polling, or SSE completion handling in `internal/terminal`.

- If the input remains usable while a chat turn is pending, every accepted turn needs an independent correlation record. A single `pendingMsgID` (or equivalent singleton) is unsafe for concurrent submissions unless the second submission is rejected locally before it reaches the backend.
- For a serialized/reject-overlap contract, reserve the active submission before launching the POST. Do not rely on `pendingMsgID` being populated by the acknowledgement: there is a pre-ack window in which a rapid second plain-text or `/chat` submission can otherwise pass the guard. Route both input forms through the same local guard, show visible `chat still processing` feedback, and issue no second request.
- Give the accepted submission a monotonic token and carry it on acknowledgement/status messages that can mutate model state. Reject stale tagged messages before changing pending IDs, busy state, transcript, polling, or SSE completion state. Clear only the active token on send failure or a verified completed/failed/cancelled terminal state, so a later message can submit normally.
- Preserve the distinction between the original queue/message ID and a promoted execution ID. Accept a verified queue-to-execution transition and keep existing polling fallback and SSE fast-path correlation intact; never let a delayed acknowledgement, status result, or mismatching `chat_response_done` replace the active identity or settle it twice. Legacy status messages that have no token may remain valid when their message ID is already correlated, rather than being rejected solely for lacking newer metadata.
- Reproduce the failure deterministically: hold the first POST before acknowledgement, attempt both rapid input forms, then deliver accepted and stale acknowledgements/status/events in both arrival orders, including a second turn after the first terminal state. Assert one POST during overlap, preserved original IDs, visible rejection, exactly-once response/task-ID rendering, and normal resubmission after completed, failed, or cancelled.
- Add model/dispatch regression coverage for polling-only and SSE paths, queued acceptance and promotion, unrelated same-project events, duplicate completion events, and stale status before and after a later turn's acknowledgement. Polling must stop only for the settled active turn and pending state must not be cleared by stale input.
- For concurrency-sensitive changes, run `go build ./...`, `go vet ./...`, `go test ./...`, focused chat tests, and the narrowest relevant chat/model tests under `-race`. Expand to `go test -race ./...` only when the concurrent behavior crosses package boundaries or the task explicitly requires repository-wide evidence.
