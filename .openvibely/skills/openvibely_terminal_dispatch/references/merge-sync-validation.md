# Merge Synchronization And Fix-Turn Validation

Use this procedure when an audit reports that an active task worktree is behind or unsynchronized with `main`, or contains unresolved merge state.

1. Work only in the intended task worktree and verify `pwd`, branch, and `git status` before changing files. This is an implementation/fix turn: do not perform the fresh read-only audit in the same turn.
2. Choose the integration shape required by the merge objective. If a merge commit is acceptable, merge the current `main` into the task branch. If the target requires a fast-forward-only merge or linear history, rebase the task implementation commits onto current `main` instead; when the branch contains earlier synchronization merge commits, replay the task-specific commits rather than preserving redundant base merges. Inspect each conflict together with its surrounding tests and source; preserve the task implementation and intervening `main` changes rather than choosing one side wholesale. Adjacent test additions may both be required, so retain both regression cases and remove only conflict markers.
3. For a merge, stage every resolved conflict and confirm `git diff --name-only --diff-filter=U` is empty before committing. For a rebase, stage each resolved file and continue with `git rebase --continue` (use a non-interactive editor when needed), confirming the rebase finishes without unmerged paths. In either route, run `git diff --check` and inspect the resulting diff.
4. Validate the integrated tree with a fresh `go build ./...`, `go vet ./...`, and `go test ./... -count=1`. Add the narrowest relevant `go test -race` invocation only when the integrated diff changes concurrency-sensitive behavior or the task explicitly requires it. Do not rely on stale binaries or pre-integration test results. Rebasing commits that both add regression coverage can expose duplicate test declarations or assertions written for pre-rebase diagnostic wording; use the fresh build/vet/test failures to identify these, remove only genuinely duplicate coverage, preserve distinct cases, and align assertions with the intentional current behavior rather than weakening production diagnostics. Because `main` can advance during a long fix turn, immediately before final validation and commit re-read `git rev-list --left-right --count HEAD...main` and verify `git merge-base --is-ancestor main HEAD`; if the base advanced, integrate the current tip, resolve affected conflicts, and rerun the full validation. An earlier clean merge is not sufficient evidence of synchronization.
5. Commit an in-progress merge with `git commit --no-edit` when using the merge route. For a rebase, verify the recreated task commit(s) and their parentage instead of creating an extra synchronization commit. In both routes, verify a clean `git status --short --branch` and confirm `git merge-base --is-ancestor main HEAD` succeeds; a fast-forward-only result should show `main` as an ancestor and the task branch only the intended implementation commit(s). Report the resulting commit/history shape and validation results.
6. After a rebase, inspect the configured/tracked remote ref (for example with `git ls-remote`) before updating anything. Rewriting a published task branch changes commit IDs: only update it after validation with `git push --force-with-lease` against the recorded expected old tip; if no published task ref exists, do not perform a force push merely because the local history was rewritten. Never rewrite or merge the protected `main` branch during this fix workflow unless the objective explicitly authorizes advancing it.
7. If the objective also requires advancing the checked-out `main`, do so only after the rebased task branch passes validation. Inspect the parent checkout with `git -C <repo> status --short --branch` and compare its local paths with the incoming diff; preserve unrelated tracked or untracked `.openvibely` learning changes, and stop if a local path overlaps the task diff rather than stashing, resetting, or overwriting it implicitly. From the parent checkout, use `git -C <repo> merge --ff-only <task-branch>`; never substitute a merge commit or force/reset operation. Verify the parent and task heads, the fast-forward result, and the preserved unrelated changes before starting the fresh audit.
8. Stop after the fix and validation. The goal lifecycle must initiate the separate strictly read-only audit from the synchronized committed state.

## Audit interpretation when `main` advances

If the task objective requires synchronization with the current `main`, a failed `git merge-base --is-ancestor main HEAD` is a material audit finding even when the newer commits appear unrelated to the implementation. Do not silently waive a failed ancestry check based only on a path-level diff or on the fact that an earlier merge was clean. Report the branch as behind, avoid edits or validation in the audit-only turn, and let a separate fix turn merge or rebase the current base and rerun validation. Only treat the older merge as sufficient when the objective explicitly names a historical base snapshot or explicitly permits post-merge base movement.

Common pitfall: a conflict limited to `internal/terminal/dispatch_test.go` can represent independent correctness coverage from the task branch and `main` (for example, quoted-title resolution and duplicate exact-title ambiguity). Preserve both tests and validate their combined behavior.
