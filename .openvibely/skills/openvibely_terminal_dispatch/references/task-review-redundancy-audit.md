# Task-Review Redundancy Audit

Use this reference when auditing task review/detail commands in `internal/terminal/registry.go` for duplicated responsibility.

- Compare every read-only entry point that can display reviews, especially `/tasks show <ref> review`, `/tasks reviews <ref>`, and `/tasks reviews list <ref>`. Verify whether each independently resolves the same task, fetches the same review collection, branches on JSON mode, and renders the same review view.
- Treat repeated task resolution plus review fetch/JSON/render branching as one responsibility when both entry points produce the same user-visible result. The smallest safe consolidation is a shared private helper for the review fetch/format path, with each command retaining only its distinct argument parsing, task resolution, and command registration behavior. The helper should be the only owner of the `ListTaskReviews` call and the plain/JSON branch.
- Keep intentional differences out of scope: do not merge paths merely because they both call a client method, and preserve each command's existing ref semantics, JSON schema, empty-state text, error handling, and selector/CLI behavior.
- For `/tasks reviews add`, identify the file/location operand with a validated structural boundary rather than treating any token ending in `:<positive integer>` as a location. An unquoted multi-word title can contain a location-shaped token such as `1:1` or `v2:1`; accepting that token truncates the title, can make `matchRef` resolve the wrong task, and shifts the intended later `file:line` operand into the comment. Add dispatch regression coverage with such titles that asserts the exact task, file, line, and comment submitted, plus wrong-task protection; keep quoted-title and malformed-location coverage intact.
- Resolve the whole token prefix against the task list for each valid location candidate, and choose the longest uniquely resolved task prefix rather than the first location-shaped token. This preserves a later location-shaped token as comment text after the real boundary, while an ambiguous or malformed task/location combination must fail before any review POST. If selector dispatch already has the selected task record, pass that resolved record through to the mutation instead of issuing a second task lookup.
- Review-comment text fidelity is a separate correctness contract from review-list deduplication. Inspect the extraction path from backend review markup through `ListTaskReviews` and the plain/JSON renderers: a generic `NodeText` helper that collapses whitespace can turn accepted multiline textarea content into spaces before both terminal and JSON output. Preserve meaningful embedded newlines and paragraph boundaries in the comment field while normalizing only structural HTML whitespace, and add a fixture/regression with a multi-paragraph comment that asserts line breaks survive decoded `--json` records and terminal rendering.
- Before filing a finding, compare the complete automation-notification inventory and inspect any plausible matching alert body. Report only an uncovered consolidation; do not re-report a review picker or missing-reference issue when the candidate concerns post-selection fetch/format logic.
- Regression coverage for a consolidation should exercise all three spellings in interactive/plain and CLI/JSON modes, assert equivalent review bodies and decoded JSON records, preserve the exact empty-review message, propagate the same backend error, and verify one review-endpoint request per invocation. Keep existing review-add and quoted multi-word-title coverage intact.
- Command-level result framing may intentionally differ between `/tasks show` and `/tasks reviews`; compare the rendered review body or structured records, not a wrapper label such as `Task` versus `Task Reviews`.
