# Task Attachment Audit Checklist

Use this reference when implementing or auditing `/tasks attachments` (or equivalent) commands across the client and TUI.

- Exercise documented examples through the real interactive `Model.runCommand` path as well as `RunCLI`. Interactive input needs quote-aware tokenization that removes matching quote delimiters and rejects unmatched quotes; preserve already-separated CLI argv values. Assert quoted multi-word task titles and local paths containing spaces, rather than relying on `strings.Fields` for interactive command lines.
- For commands combining a free-form task reference with file or attachment operands, identify the boundary structurally and keep the parsed task and operand values separate. In particular, attachment-delete confirmation text must use the exact resolved task title and attachment ID/filename; never derive the destructive target from only `args[len(args)-1]` when an operand can contain spaces.
- Typed target-result handling and attachment-picker dispatch may intentionally have different task/attachment lookup, selection, stale-message, and session/project-scope boundaries. Do not merge those resolution paths merely because they both delete an attachment. Once each path has a current resolved task and attachment, route both through one small terminal-local helper that accepts the current model, selected project ID, and those resolved records. That helper must construct the same `Task Attachments` command, canonical fallback labels (attachment filename/ID and task title/ID), confirmation wording, `--force` hint, and callback to the shared deletion-result renderer. Leave confirmation timing, selector construction, stale-result guards, lookup timing, and headless `--force` behavior in their existing callers. Add direct typed-versus-picker parity coverage for pending confirmation text, no pre-confirmation mutation, confirmed refreshed rendering, and fallback labels.
- When typed CLI and interactive confirmation callers need one source for prompt wording and `--force` guidance but intentionally use different display labels, extract a label-aware confirmation wrapper rather than merging their lookup or mutation flows. Pass canonical resolved labels from the interactive path and preserve the CLI caller's raw operands for its existing guidance, including operands containing spaces. Keep CLI lookup deferred and assert the exact raw-label guidance together with zero `DELETE` requests when `--force` is absent.
- Require a selected project for every attachment read and mutation, send the selected `project_id`, and validate response task/project markers and delete-control scope before rendering a success. Preserve old unscoped public task-detail behavior when adding a scoped variant: do not populate newly introduced structured attachment records through a legacy `GetTask` call that has no project context; route attachment-aware callers through an explicit scoped method.
- Do not treat a successful upload HTTP response or refreshed attachment list as proof that every requested file was persisted. The backend may skip an individual oversized, unreadable, copy-failed, or repository-failed file while returning `200` when at least one file succeeds. Ensure the client/dispatch path exposes partial success or otherwise verifies each requested file before claiming completion; never report `len(filePaths)` as uploaded without per-file evidence. Add mixed-success/mixed-failure regressions for both TUI and CLI, in addition to all-file failure and all-file success.
- When the backend exposes only the refreshed list, the established client-side verification is a scoped pre-upload snapshot followed by a scoped post-upload parse: collect the stable IDs that existed before the POST, match only newly returned records to the requested multipart basenames as a multiset, and return the refreshed list together with a typed partial-upload error containing matched records and missing names. This handles pre-existing and duplicate filenames without treating an old row as evidence for a new upload. TUI and CLI callers must propagate that error and omit any inflated all-files success message.
- A preflight snapshot adds a `GET /tasks/\u003cid\u003e?project_id=\u003cselected\u003e` before the multipart POST. Make attachment fixtures method-aware so the GET returns the prior snapshot and the POST returns the refreshed fragment; keep POST-level failure tests returning a successful snapshot first, otherwise they only test preflight failure. Assert the mixed result's successful details and missing names through client, interactive TUI, and CLI paths.
- Cover the complete failure matrix: upload server failure, confirmed-delete server failure, and their CLI equivalents must expose the error without a success claim; cancellation and CLI no-force rejection must issue no mutation. Pair request-shape tests with refreshed-fragment, scope-mismatch, mixed-upload, and output assertions.
