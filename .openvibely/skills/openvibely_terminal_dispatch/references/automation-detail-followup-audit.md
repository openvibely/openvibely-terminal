# Automation Detail Follow-Up Audit

Use this checklist after an automation-detail parser hardening pass, especially when a read-only audit reports that ordinary tests are green but malformed or partial HTML may still be misleading.

## Numeric Fallbacks

- Treat a present numeric attribute as a tri-state result: absent, valid, or malformed. Return the malformed state to the caller. A malformed runtime total or external tracked-resource attribute must suppress visible-text recovery for that same metric; otherwise invalid structured data can become a confident value through `namedAutomationCount`.
- Check conversion errors everywhere, including ARIA-derived counts. Do not assign an available zero when `strconv.Atoi` fails or overflows.
- Parse text counts as complete tokens. Require a real separator between label and number, reject signed, decimal, concatenated, trailing-garbage, qualified-prefix, and punctuation-plus-garbage forms such as `running 2,garbage`, `2 running;garbage`, `- 2 running`, and `not 2 running`, and keep malformed values unavailable with a warning. Validate both the text before a number and the full continuation after it; accepting a delimiter is not enough if another unapproved token follows.
- Preserve invalidity per metric. If one structured count field is malformed, independent valid fields may still be used; do not mark every sibling field malformed merely because a shared structured payload failed. Fields not actually claimed by the malformed payload may retain their own valid fallback source.
- A truncated or otherwise undecodable structured JSON object can leave the decoded map non-nil but incomplete, not only nil. Scan the raw payload for every recognized claimed key whenever decoding fails or trailing input exists, mark those fields malformed/unavailable, and leave only unclaimed fields eligible for independent text or explicit-attribute sources. Never treat raw key presence as a valid numeric value, and fall back to all-field invalidation when no recognized claimed key can be identified, including malformed objects that contain only unknown keys.
- Treat the backend's exact normalized `No active work` node label as an explicit all-zero report when that label is the documented fallback for a node with no activity. Mark all five node metrics available with value zero only for the exact label, not for arbitrary prose containing similar words; add a regression so ordinary zero-count nodes do not render as unavailable dashes.

## Record Retention And Rendering

- Never silently drop a marked graph or detail record merely because it lacks an ID, key, name, valid metric, or parseable count. A marked graph record is authoritative graph topology and should remain in the graph-node/edge collection with an explicit warning even when no identity can be recovered; a detail record that cannot correlate to an authoritative graph row belongs in a separate unmatched/unknown collection. This applies to identity-less, count-less, and malformed count-only edges as well as node details. Avoid early returns that discard a marked record before it is appended.
- Do not return early from node rendering after printing an empty or unavailable authoritative graph. Retained unmatched detail records must still be rendered when the graph-node slice is empty or `GraphAvailable` is false, including their per-field available counts and an explicit correlation-unavailable note.
- When `GraphAvailable` is false, render retained graph-origin and detail-only edge records as well as node records. An unavailable-graph message must not silently hide source/target topology, labels, conditions, or available transition counts recovered from a partial fragment; keep edge provenance and correlation-unavailable warnings visible while still reporting that the live graph itself is unavailable.
- Keep authoritative graph rows and unmatched detail rows separate. Aggregate availability flags used for legacy compatibility must be derived from the rows being rendered, not from unrelated unmatched records; unmatched detail metrics must not make every graph row appear to have confident zero counts.
- Preserve representation provenance through rendering. Rows retained from a graph marker are authoritative graph diagnostics even when `GraphAvailable` is false; do not relabel them as `Detail-only nodes` or render them as if the detail panel were the source. Render genuinely detail-only rows separately, and keep an unavailable-graph message from being contradicted by a graph-origin table.
- Prefer per-record/per-field availability over broad aggregate flags. A populated metric in one record must not make missing sibling metrics display as zero.
- If an ARIA label is present and appears intended to describe transition counts but fails the complete grammar, preserve the edge record and add a malformed-count warning/partial state rather than silently treating it as absent. Do not let another edge's valid count make the malformed edge or the whole section look confidently complete.

## Identity Joins

- Validate all stable identity dimensions that are present before merging node records. An ID match or a key match alone is not sufficient when both records expose the other dimension: a detail record whose ID matches one graph node but whose key matches another must remain unmerged and warned rather than attaching counts/configuration to whichever candidate is encountered first. Likewise, duplicate records with conflicting IDs must not collapse merely because their keys match; require compatible identities and preserve the conflicting record separately.
- Apply the same conflict rule to edges. A shared edge ID or key does not override contradictory source/target endpoint identity or other stable edge identity; reject the merge, retain both topology records, and mark correlation unavailable. Check endpoint conflicts before the early stable-ID/key success path.
- Do not let a merge algorithm's first matching row establish correlation when later identity fields contradict it. Collect all candidate records, validate uniqueness and pairwise compatibility, then merge only a uniquely verified pair. Add reordered-input regressions for conflicting node ID/key pairs and shared edge ID/key pairs with different endpoints.
- Freeze each parsed candidate's stable correlation identity and deterministic tie-break key before merging or enriching any graph row. Do not recompute a candidate's identity after a prior merge fills its missing ID or key, because an ID-only and key-only alias can otherwise become order-dependent. Treat identity-less candidates as distinct records rather than placing them in one shared duplicate bucket.
- Do not deduplicate graph or detail edge candidates while initially parsing them. Preserve the complete candidate sets, inspect duplicate stable IDs/keys and endpoint compatibility, and establish correlation uniqueness before merging any pair. Equal-quality conflicting metrics must not be selected by traversal order, and a first graph edge must not consume a detail edge or hide another compatible candidate; retain ambiguous records independently with deterministic tie-break ordering.
- Evaluate edge correlation uniqueness bidirectionally across the complete graph/detail candidate sets. It is not enough for each detail record to see one compatible graph record and itself as the only detail candidate: one incomplete graph record can still be ambiguously compatible with multiple contradictory detail records. Require the compatible relation to identify exactly one graph candidate and exactly one detail candidate before merging; otherwise retain every candidate independently and warn, with output independent of detail traversal order.

## Textual Count Prefixes

- Validate the complete context before a numeric count, not only the final punctuation immediately before the number. Prefixes such as `status: 2 running`, `maybe, 2 running`, and `not:2 running` are qualified or negated statements, not approved count labels; reject them, keep the metric unavailable, and emit the malformed-count warning. Approved separators do not make arbitrary preceding prose valid.
- Test both label-before-number and number-before-label forms with unknown qualifiers, negations, punctuation, decimals, signs, concatenation, and trailing words. A parser that accepts one valid-looking segment inside otherwise unapproved prose can turn ambiguous text into a confident metric.

## Deterministic Output

- Stable sorting requires a total order for retained duplicates, not merely a primary display key plus `sort.SliceStable`. Include every distinguishing identity and display/metric field needed to order same-name nodes and same-endpoint/label edges with different counts or source provenance. Do not let input/document order decide the visible order of valid duplicate records.
- Preserve the source order of distinct topology rows when it is an existing contract. In a mixed collection, localize deterministic tie-breaking to duplicate same-representation stable-identity groups (for example, sort duplicate values back into their original index slots) instead of globally sorting all edges; otherwise a hardening pass can reorder ordinary backend graph rows and change established output or metric expectations.
- Add renderer regressions that permute input records and compare stripped output for node, edge, resource, unmatched-detail, and warning ordering. Keep relation in resource identity and sort keys, and include explicit tie-breakers for duplicate node/edge rows.
- Duplicate resource rows with the same complete identity (node identity, resource type, resource ID, and relation) must not be retained by first-seen traversal order when display fields differ. Choose or merge a canonical record deterministically using the full display-field tie-break key, and prove that permuted fragments produce identical parsed records and JSON; relation-distinct rows remain separate.

## Regression Matrix

Add focused fixtures for malformed runtime and external numeric attributes with visible fallbacks, overflowing ARIA values, punctuation/trailing-garbage text counts, qualified-prefix text, malformed structured payloads with valid independent fields, non-nil partial JSON decode results, unknown-only malformed JSON objects, identity-less graph records, identity-less and malformed count-only edges, conflicting node IDs/keys, shared edge IDs/keys with contradictory endpoints, empty or explicitly unavailable graph plus retained detail records, unmatched malformed edges, and aggregate-availability isolation. Also cover unavailable graphs with retained graph/detail edge rows and duplicate same-identity graph/detail edges with conflicting equal-quality metrics in both input orders. Assert both parser flags/warnings and stripped plain output; also assert valid independent values remain available, malformed marked records remain visible, graph-origin rows are not mislabeled as detail-only, and reordered input produces deterministic output.
- Include an exact `No active work` fixture that verifies all five node metrics are explicitly available at zero, while similar but non-exact prose remains unavailable or warned.
- Include a one-to-many edge-correlation fixture: one incomplete graph edge and multiple contradictory detail edges sharing a stable identity must remain separate, warn, and serialize identically under detail-record permutation.
- Include duplicate same-identity resource fixtures with different names/statuses/URLs in both input orders; assert deterministic canonical selection and preservation of relation-distinct rows.

## Additional Hardening From Fresh Audits

- Separate graph presence from detail presence. Only a graph panel or authoritative graph-node/graph-edge markers may establish `GraphAvailable`; detail-panel markers may establish that detail topology was returned, but must not make an unavailable graph look loaded or cause a version to be inferred as published. Keep graph-origin provenance independent from `NodesAvailable`/`EdgesAvailable`.
- Treat node names as display-only. A marked graph node with a name but no stable ID or node key is still retained, but it must carry an identity/correlation warning and partial state. Never use a name alone to join graph and detail nodes; names are not unique stable identities.
- Resolve joins against the complete candidate set, not incrementally against the first row. If duplicate graph or detail rows expose the same ID/key, or if an identity can match more than one compatible row, do not merge any ambiguous pair. Retain the records independently and warn. Equal-quality duplicate metrics must not be selected by document order; if duplicates are intentionally rendered, their output requires deterministic field-level tie-breakers.
- Apply candidate uniqueness to edges with incomplete data as well as fully populated edges. A shared edge ID/key with multiple contradictory or partially identified endpoint candidates must not attach a detail record to the first matching topology row. Merge only a uniquely verified compatible pair; retain ambiguous records and surface correlation unavailable.
- Inspect verified ancestors when parsing the live route. The backend may wrap a trigger/agent graph node in a task link and place its runtime-count summary in the ancestor `aria-label` while the node subtree contains only a model label. Read that ancestor only when its semantics identify the same node, use it as a lower-quality per-field fallback, and preserve explicit structured invalidity and provenance. Add a fixture for model-labelled nodes so common runtime counts are not silently reported as unavailable.
- Make warnings deterministic wherever they cross a parser-to-output boundary. Source traversal order can vary when equivalent markup is reordered, so sort or otherwise canonically order warning records before plain rendering and JSON serialization while preserving meaningful duplicates/context. Add a reordered-input regression that compares warnings as well as rows.
- A case-folded sort key is not a total order. When stable identities or display fields differ only by case, append the original case-sensitive fields and remaining identity/metric tie-breakers after the normalized key. This applies to resources as well as nodes and edges; `sort.SliceStable` must not leave valid case-only rows in input order.

During a strictly read-only audit, inspect these paths and tests without running mutating commands or changing the workspace. Apply any fixes in a separate implementation turn, run focused tests followed by the repository validation, and then perform a fresh audit from scratch.
