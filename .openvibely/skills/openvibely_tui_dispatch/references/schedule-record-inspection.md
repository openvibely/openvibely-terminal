# Schedule Record Inspection

Use this workflow when adding or auditing `/schedule show` or an equivalent read-only schedule inspection action.

- Keep one canonical read action. Prefer `show`; if `open` is retained for discoverability or compatibility, normalize it to the identical handler and document that alias in registry/help metadata.
- A missing schedule reference should open the searchable selector only in interactive TUI mode. Headless mode must return deterministic usage/error output and must never fetch solely to prompt.
- Resolve schedule references with the shared resource matcher: exact full ID or exact name first, then unique ID prefix, then unique substring; reject ambiguous and unknown references locally. Picker selection must reuse the fetched schedule record or canonical reference so it does not repeat the schedule catalog request.
- Parse and store the schedule's canonical human name separately from timing, recurrence, status, or other rendered card text. Do not use the complete card text as the matcher name: an input equal to the visible name then degrades to a prefix match and can become ambiguous when another schedule starts with the same name. Test with realistic nested title/detail card markup and a second schedule whose name starts with the first name, then assert exact-name precedence.
- Treat a schedule record and its bound task as distinct resources. Read the schedule from the selected project's complete schedule catalog, then verify/open its `task_id` through the project-scoped exact task metadata/detail route used by the web UI. Do not search only the task board: scheduled-category tasks may be valid while absent from board listings.
- Include `project_id` on every schedule and bound-task request. Render unavailable only when the exact lookup authoritatively reports absence, normally HTTP 404, which may represent a deleted or inaccessible target. Authentication, transport, HTTP 5xx, decode, malformed-detail, and identity-validation failures must remain command errors. In particular, a successful detail response with a missing task marker or mismatched task/project identity is not proof of absence and must not be converted to unavailable. Use a typed status error or predicate rather than matching error strings or a broad category such as `IsReachableError`; preserve existing user-facing error text while enabling `errors.As` classification. Add regressions for 404, 5xx, malformed detail, missing identity, and foreign identity.
- Render schedule ID/name, bound task identity, status/configuration summary, and a copyable `/tasks open <task-id>` action when the target is available. Sanitize backend-controlled schedule and task text for terminal output.
- Keep inspection strictly read-only. Add dispatcher-level regressions for explicit refs, omitted-ref selection and cancellation, canonical/alias parity, exact-name/full-ID/prefix/substring matching, ambiguity/unknown errors, unavailable task targets, identity failures, no-project guards, pagination, request counts, project query propagation, terminal safety, and zero mutation requests. Assert cancellation performs no bound-task lookup.
