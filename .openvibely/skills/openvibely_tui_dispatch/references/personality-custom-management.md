# Personality Custom Management

Use this reference when extending the shared `/personality` command surface.

- Keep the bare `/personality` no-argument rendered-page behavior intact, but parse explicit actions rather than letting unsupported action words fall through to the legacy read path. Unknown actions should return clear usage and make no request.
- The supported reference actions are `list`, `show <key|name>`, `add`, `edit <key|name>`, `set <key|name>`, and `delete <key|name>`. Use the shared `matchRef` semantics (exact, unique prefix, unique substring, then ambiguity/unknown errors) for built-in and custom entries.
- A missing reference for `show`, `edit`, `set`, or `delete` opens the personality selector in TUI mode; headless CLI mode preserves the usage error. Selector candidates should reuse the records already fetched for the selector instead of issuing a duplicate list request. Keep the base/built-in sentinel available for discovery but exclude non-editable base entries from edit/delete choices when the backend contract requires it. Regression-test both direct edit/delete references to Base (no mutation and the expected local error) and the selector’s omission of Base for those actions.
- Preserve the existing preset `set` behavior while allowing custom keys. Route destructive custom deletion and built-in reset/override operations through the normal TUI confirmation path and require CLI `--force`; cancellation or refusal must not report success.
- Render list records with stable key, name, type, description, preview, and active fields, show an empty-state creation hint, and render the full system prompt for detail. Give CLI JSON records explicit snake_case tags and keep empty collections as `[]`.
- When an edit returns a JSON resource, the backend update/detail response may omit list-only state such as `active`. Preserve `Active` from the resolved list entry, alongside `IsPreset` and `HasCustom`, before rendering or marshaling the edit result; a successful edit of the currently active personality must not report `active:false`. Add an active-entry JSON edit regression for this response-shape boundary.
- Use the unambiguous add grammar established by the TUI: `name | system prompt` leaves the description empty and treats every character after the first separator, including later `|` characters, as prompt text; `name | description=<description> | system prompt` sets the optional description. The explicit `description=` marker is case-insensitive and is recognized only at the first post-name field boundary; `description:` is ordinary literal prompt text in the two-field form. Keep the marker reserved for this structural purpose, trim fields, require non-empty name, description, and prompt, and reject missing separators, blank marked fields, malformed marked syntax, or a dangling separator with a clear usage/error before issuing any backend mutation. Keep the client payload explicit, including an empty description for the two-field form.
- Test the marker boundary with a valid two-field command whose prompt starts with the literal `description:` (with and without later pipes); it must keep an empty description and the complete prompt. Do not infer an optional description from an arbitrary second pipe or by scanning the whole post-name remainder. Add parser and decoded-payload regressions through both interactive dispatch and the headless CLI argument boundary.
- For `edit`, use a bounded four-field split: ref, name, description, and the remainder as system prompt. Do not use an unbounded `strings.Split` that turns prompt content into extra fields or silently changes the description. Trim and validate required fields after splitting, and reject malformed operands before any mutation.
- Test the parser matrix explicitly: two-field add with a literal pipe in the prompt, two-field add with a prompt beginning with the literal `description:` marker and no later pipe, two-field add with that prefix plus later literal pipes, marked optional-description add with one or more literal pipes in the prompt, empty required fields, missing or malformed marker syntax, and edit prompts containing pipes. Pair parser assertions with decoded backend payloads so a passing command does not hide a misassigned description or prompt. Run the matrix through both interactive and headless CLI argument boundaries, assert exactly one create POST for valid inputs, and assert zero mutation for malformed inputs.
- Surface backend validation, duplicate, not-found, and other operation errors without refreshing them into success output. Add client, TUI, and CLI coverage for malformed, unknown, duplicate, ambiguous, canceled, forced, and failed operations alongside no-argument selector cases; assert that failure paths make no unintended follow-up mutation or success report.

Route each existing label call site through that helper while leaving layout, styling, CRUD, selection, project scoping, JSON output, active-state handling, and descriptions unchanged.

## Direct-Command Resolver Consolidation

When auditing or implementing direct `/personality` actions, compare `show`, `edit`, `set`, and `delete` for duplicated full-list resolution. If each branch independently calls `ListPersonalities` and then applies the same `matchRef` semantics before its action-specific work, treat that as one lookup responsibility rather than four unrelated similarities.

The smallest safe consolidation is a private resolver that returns the canonical personality record (and its lookup error), reused by those branches. Keep action-specific mutation, confirmation, preset/custom behavior, JSON/plain rendering, and selector/CLI missing-reference behavior unchanged. Regression coverage should verify identical exact/prefix/substring and ambiguity handling, one list request per direct invocation, and zero mutation for unknown or ambiguous references. Before filing an audit finding, compare the complete automation-notification inventory and inspect plausible alert bodies; keep this resolver duplication distinct from display-label consolidation, selector re-fetch avoidance, and the former edit-handle correctness issue.
