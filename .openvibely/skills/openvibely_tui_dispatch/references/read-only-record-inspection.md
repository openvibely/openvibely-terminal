# Read-Only Record Inspection Commands

Use this pattern when exposing an existing backend collection of audit, vote, decision, or trace records, or a repository-local indexed collection, through both the interactive TUI and one-shot CLI.

- First audit current backend Swagger, route registration, handlers, and web behavior. If no public project-scoped list/read/search route exists, do not guess HTTP endpoints or add a backend source of truth. Use only an existing selected project's repository path and canonical index when repository-local inspection is explicitly in scope; otherwise report the feature as unsupported.
- For backend-backed collections, keep the feature read-only and reuse the existing client method and authoritative route. Choose the narrowest existing command namespace that already owns the resource; do not add a speculative alias or backend endpoint. Make one client read per invocation and preserve the existing request path/query contract.
- For HTML/HTMX alert detail fragments, verify the current handler/template markers and issue exactly `GET /alerts/<id>/details?project_id=<selected>`. Parse multiline body content from the stable `data-alert-markdown`/`data-raw-content` marker regardless of its element tag, and parse structured metadata from the detail-loaded metadata marker rather than a copy-source `<pre>`. Preserve line breaks, decode absent metadata to a non-nil empty map, and reject an empty project ID before any request so the route cannot become unscoped.
- For a show/inspect command backed by a list plus detail route, compose the result from one project-scoped summary lookup and one detail request for an explicit reference. When an interactive selector already fetched candidates, carry or reuse the selected canonical record instead of issuing a duplicate list request; preserve the same exact-title/ID-prefix/ambiguity behavior in both modes.
- For repository-local indexed resources such as `.openvibely/memories/MEMORIES.md`, treat the index as authoritative: read only handles declared there, do not enumerate arbitrary files, reject absolute, empty, and traversal references, ensure cleaned paths remain beneath the canonical root, and reject symlink escapes. Apply the same containment/symlink policy to the canonical index before opening it; do not join and read `MEMORIES.md` directly. Keep OS paths and filesystem errors out of user output; warnings should be safe and bounded.
- Before opening either the index or an indexed topic, verify the resolved target is a regular file. Reject directories, FIFOs, devices, sockets, and other special files so a bounded `ReadAll` cannot block indefinitely; if a symlink is allowed within the root, validate its resolved target and re-check the opened descriptor's file type. Context checks alone do not make a blocking special-file read cancellable.
- Preserve useful partial records from malformed entries while exposing explicit warnings. Distinguish missing or empty indexes, malformed entries, unsafe/symlink-rejected references, special-file/read failures, and file read/decode failures so plain and JSON output can explain partial or unavailable state without leaking repository paths. Every path-rejection branch in list/show/search should produce the same safe warning or typed unavailable result; do not silently omit a rejected entry.
- Parse the documented index structure, not any line containing the substring `.md`. Accept only an actual Markdown link or a validated explicit filename token supported by the canonical index format, and require the token to be a real safe topic handle. Add a prose fixture containing `.md` that must not create a phantom entry or trigger a file read.
- If a list command accepts a metadata filter, keep filtered-empty distinct from a genuinely empty index. Pass the filter/context into the renderer or use a dedicated no-match renderer so the output says no records match the filter rather than claiming that the index has no topic files.
- If the backend exposes no curation route, keep commands read-only: do not advertise edit/delete, infer mutations from file existence, or create a second mutation authority. Document the read-only limitation when users need correction or removal guidance.
- Treat user-provided path identifiers as path parameters: escape them at the URL construction boundary, and test the raw request target for reserved characters rather than only asserting the server's decoded path.
- Require the selected project before dispatch when the command is project-scoped, and require exactly one step/resource reference. Reject unresolved or ambiguous references locally before opening a selector or issuing HTTP in headless mode; preserve the normal nonzero CLI error behavior.
- For human output, identify the requested execution/resource explicitly, copy records before sorting, order them by stable record fields, sanitize displayed values to one line, and bound long reasoning or other free-form text for terminal readability. A line-count cap alone does not bound a single very long line: cap bytes/display cells as well, normalize or strip terminal control/ANSI sequences, and apply the policy to body text, titles, summaries, snippets, and user-supplied query text.
- For composite alert inspection, keep Markdown body line breaks readable in plain output, show explicit empty-body/empty-metadata states (including an overall empty-detail state), and preserve the full decoded body rather than applying summary truncation. In JSON mode, emit only stable decoded data with no banner or ANSI, represent body and metadata emptiness explicitly (`""` and `{}` rather than null where the contract requires), and retain summary plus full detail in a stable nested shape.
- Treat client-generated errors as human output too: sanitize and bound every index-derived handle, title, query, and ambiguity candidate before appending or rendering it. Keep canonical raw references separate for dispatch, and do not assume generic `err.Error()` presentation performs terminal sanitization.
- For `--json`, marshal the decoded records directly with no banner, ANSI styling, or human labels. Normalize a `null` collection to a non-nil empty slice so empty output is `[]` rather than `null`, and keep JSON tags/schema stable. For composite inspection results, apply the same rule to every collection, including warnings.
- Add focused client tests for exact method/route, escaped references, multiple records, empty/null payloads, malformed responses, and request count. For repository-local parsers, also test canonical-index-only reads, missing/empty/malformed entries, prose containing `.md`, traversal/absolute references, canonical-index and topic symlink escapes, special files, partial warnings, bounded/control-character-safe output, and secret/path redaction. Add dispatch/CLI tests for success, filtered no-match, empty, JSON, unauthorized, server errors, decode failures, unresolved/ambiguous refs, and no-project/operand guards. Confirm existing neighboring commands retain their request counts and output behavior.
- When inserting additive tests into large existing Go test files, anchor on a complete unique function boundary, then run `gofmt` and a focused build/test immediately. Inspect the neighboring declarations if the compiler reports a top-level syntax error; insertion-anchor mistakes can leave a prior test body detached while production code remains valid.
