# Worker Limit Numeric Validation

Use this checklist when auditing or changing `/workers limit` and `/workers project` numeric operands in `internal/tui/registry.go`:

- Treat `0` as an intentional, meaningful value (unlimited) only when the user explicitly supplies a valid zero. Never let blank, nonnumeric, negative, or overflowing input fall through to zero.
- Avoid `atoi` or hand-rolled digit accumulation when the parsed value is sent as an `int`; overflow can wrap a huge operand to `0` on a 64-bit build and silently remove the worker cap. Use a checked decimal parse with the target integer width (`strconv.ParseInt(..., 10, strconv.IntSize)` or an equivalent checked parser), then validate the command's allowed range.
- Validate operand cardinality as well as numeric content. Once the command's expected numeric operand has been identified, reject any surplus or trailing operands rather than parsing `rest[0]` and silently ignoring the rest. Return the existing local usage/error path before issuing `UpdateWorkerLimit` or any `/workers` request. Apply the same boundary to both global and project-scoped commands.
- Regression-test ordinary positive values, explicit `0`, negative values, nonnumeric values, empty operands, `math.MaxInt`/the largest accepted value, and an overflowing value such as `18446744073709551616`. For invalid and overflow cases assert a nonzero/actionable error, no mutation request, and no misleading “unlimited” success output; for explicit zero assert the intentional unlimited request and message.
- Add dispatch regressions for a valid numeric value followed by one or more extra tokens on both global and project-scoped worker-limit commands. Assert an actionable usage/validation error, zero mutation requests, and no success transcript; do not treat the extra tokens as ignorable input.
- Prefer an end-to-end dispatch test with a test server that inspects the posted `max_workers`, because a parser unit test alone will not catch an incorrect request or success rendering.
