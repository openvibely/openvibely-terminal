# Model Command Project Scoping

Classify `/models` and its singular `/model` alias by action instead of applying one blanket project guard. Bare listing, `list`, and filtered model listing are project-independent reads: they must work in interactive and headless modes with zero, one, or multiple projects and must not require `m.selectedID` or an implicit `-project`.

For global model listing, omit `project_id` from the model request. Do not let CLI preload or output setup turn a global read into a project-scoped operation, and do not fall through to an arbitrary backend project when no project is selected. Preserve the global JSON contract as a raw, non-nil model array, including `[]` for an empty result; do not add an implicit-project wrapper merely because exactly one project exists.

Keep project guards for project-dependent actions such as `capacity`, `default`, and `delete`, plus any future model operation whose backend contract requires project context. Parse/classify the action before calling `m.needProject()`, copying `m.selectedID`, resolving a ref, opening a selector, or entering confirmation. For guarded interactive actions, return the local no-project guidance without issuing a request. For headless actions, preserve the single-project convenience when it is an established contract, require explicit `-project <name|id>` for zero or ambiguous/multiple-project scope, and mention first-project creation when there are no projects.

Carry the selected project ID on every scoped lookup, capacity/enrichment request, default mutation, and delete mutation. Never use an unscoped model lookup as a fallback for a guarded operation. Keep selector, confirmation, cancellation, refresh, and mutation error behavior unchanged apart from the action-level scope decision.

## Resolved Model Actions

When typed-reference and picker routes for `/models default` or `/models delete` converge on an already resolved `client.LLMModel`, share only the post-resolution action in a small local executor. Let that executor accept the canonical model and action, perform exactly one `SetDefaultModel` or `DeleteModel` call with the model ID, short-circuit mutation errors, produce the success status, and construct the scoped refresh/rendered output. Preserve route-specific listing and `matchRef` behavior, picker construction and cancellation, deletion confirmation text and timing, busy-state changes, JSON/plain rendering, and selected-project capture outside the executor; do not generalize the helper across unrelated resources.

Preserve the established fallback contract: a mutation failure returns the error with no success text and no refresh, while a refresh failure after a successful mutation returns only the success status. Regression tests should exercise the 2-by-2 typed/picker and default/delete matrix and assert one canonical mutation per route, equivalent refreshed output, project ID propagation, and no duplicate post-resolution lookup. Also pin unknown and ambiguous typed refs, picker `Esc`, both delete confirmation forms before mutation, mutation failures through both routes, and post-success refresh failures.

Regression-test the actual interactive and CLI dispatch paths across zero, single, and multiple projects. Cover global bare/list/filtered reads and scoped capacity/default/delete actions in plain text and JSON modes; assert global request queries omit `project_id`, scoped requests include the intended ID, zero requests occur when a scoped action lacks a project, and global JSON remains a raw array. When checking query scope, use the recorder's full-URI helpers or exact URL snapshots, such as `sawQuery` and `urlsSnapshot`; do not rely on path-only or query-stripped aggregates like `all()`, because they can make a request carrying `?project_id=...` appear unscoped. Finish with focused model tests, `go build ./...`, `go vet ./...`, uncached `go test ./... -count=1`, formatting, and `git diff --check`; isolate any unrelated pre-existing race failure while running race coverage for changed model tests.
