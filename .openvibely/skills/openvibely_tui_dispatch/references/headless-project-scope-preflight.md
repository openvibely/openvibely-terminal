# Headless Project-Scope Preflight

Use this checklist when changing headless CLI project loading or dispatch in `internal/tui/`.

- Keep implicit project selection mode-specific. Interactive TUI startup may retain its existing first-project behavior, but headless loading must not install the first project when `-project` is omitted and multiple backend projects are returned.
- Run one centralized CLI-only scope preflight after project loading and before status, stream setup, command dispatch, selector work, or any project-scoped endpoint. Classify commands from the registry so global/offline paths such as help, `projects list`, `projects create`, and login remain usable without a project reference.
- For an ambiguous implicit scope, fail nonzero with actionable `-project <name|id>` guidance. This guard must cover read-only, mutating, and forced-destructive commands; assert that no project endpoint or mutation is called before the error. With zero selected projects, preserve the existing local no-project error behavior rather than allowing backend fallback.
- Preserve explicit resolution semantics: full ID, exact name, and unique ID/name prefix must select the requested project and carry its `project_id` on every project-scoped request. Do not change ambiguity or unknown-reference errors.
- Preserve the single-project no-flag convenience, but make the implicit target auditable in successful output. Expose a stable project name and ID (or an equivalent scope field) in human and JSON output without reshaping unrelated resource data unnecessarily; apply this only where the project was implicitly selected if that is the existing output contract.
- Regression-test the matrix across plain text and JSON, read-only and mutating commands, forced destructive commands, zero-project behavior, global command exemptions, explicit name/full-ID/unique-prefix selection, and exactly-one-project output. Use request counters or handlers that fail on unexpected project calls to prove the preflight runs before I/O.
- Finish CLI changes with `gofmt`, `go build ./...`, `go vet ./...`, `go test ./...`, and race tests when the changed model/loading path involves asynchronous work. Review help, README examples, and the final diff for accidental interactive behavior changes.
