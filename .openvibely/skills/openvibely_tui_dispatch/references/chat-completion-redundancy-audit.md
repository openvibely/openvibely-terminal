# Chat-Completion Redundancy Audit

Use this reference when auditing chat completion handling in `internal/tui/model.go`.

- Compare the terminal-status polling branch with the SSE `chat_response_done` fast path at the level of state transitions, not just client calls. In the observed implementation, both paths clear the pending-chat ownership state, mark the model idle, and append the agent reply; this is one finalization responsibility even though the entry conditions and payload sources differ.
- Consolidate only that shared finalization into one narrow private model helper. Let callers retain their distinct scheduling and guards: polling/fallback behavior, SSE project and pending-chat correlation, foreign-event rejection, and the SSE fast path's no-extra-status-request behavior must not move or change.
- Make the shared helper delegate to the canonical pending-chat cleanup function rather than manually clearing a subset of fields. Submission-serialization state such as `chatSubmissionPending` can be added alongside the pending IDs; omitting it leaves the model permanently busy from the user's perspective and rejects the next message even though the response was rendered. Verify every terminal completion path resets the full ownership state before allowing resubmission.
- Preserve optional polling-only metadata. Polling can also receive created task IDs and render them, so the helper should accept optional task metadata or the polling caller should perform that additional rendering outside the shared state transition; do not discard it while deduplicating.
- Regression coverage should exercise terminal polling completion, inline SSE completion, polling completion with created task IDs, and an unrelated or rejected SSE event. Assert the pending-chat fields, submission guard, busy/idle state, appended reply, task-ID output, and request count so consolidation does not reintroduce an unnecessary status fetch on the SSE fast path.
- Before filing a redundancy suggestion, distinguish this post-completion state transition from separate correctness findings such as overlapping sends, stale-event correlation, or duplicated status-fetch request construction. Those may share nearby code but represent different responsibilities and should not be conflated.
