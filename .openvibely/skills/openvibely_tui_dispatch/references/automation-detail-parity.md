# Automation Detail Parity

When auditing or extending `/automations`, compare the terminal's summary/lifecycle surface with the backend's project-scoped automation detail contract. A list that renders only `ID`, name, and state is incomplete when `GET /automations/:automationId` exposes a live workflow graph, including node/edge state, active work counts, resources, or external-state information.

If the detail route exists but the TUI has no detail/show workflow, treat the gap as a product-surface parity finding rather than a lifecycle-action bug. A terminal-native implementation should provide an interactive selector for a missing automation ref and a headless CLI-compatible detail action, carry the selected `project_id` through the detail request, and render the graph/status information without changing existing run-now, pause, resume, or delete behavior.

## Implementation Contract

- Verify the current handler and template before coding. The live route is an HTML/HTMX response rooted at `#automation-live`, not automatically JSON; use semantic `data-*` markers and structured sections first, with current SVG/details/ARIA labels only as verified fallbacks. Keep transport and parsing in `internal/client`, not in command handlers.
- Treat the rendered handler/template output as the response contract, not the backend service model. A service may compute active totals, resources, or external state while the live HTML intentionally omits them. Audit the real route, generated/representative markup, and backend integration assertions; do not make synthetic client fixtures stand in for fields the endpoint does not render. Classify omitted fields as an explicit backend contract gap and render them unavailable rather than fabricating values or claiming parity.
- Keep detail data separate from the list `Automation` model. Parse metadata, version, graph nodes/edges, runtime totals, resources, and external state independently, with an explicit presence/availability flag for every optional section, aggregate, and per-record metric where zero is a valid value. Missing, empty, or malformed optional data must render as `unavailable`, `not reported`, or `partial`, never as a loaded zero or a fabricated graph.
- Do not let one record's metric presence imply that every sibling record has metrics. Preserve explicit zero counts as reported, but render an absent node or edge metric as unavailable; aggregate `NodeCountsAvailable`/`EdgeCountsAvailable` flags are insufficient when rows can be partial.
- When the same record appears in structured attributes and compact visible text, track availability and source quality per metric. Structured count attributes are authoritative over visible labels, while labels may fill only fields that are still absent; never use `value == 0` as the test for missing data, and never let a lower-quality text fallback overwrite an explicitly reported zero. The provenance/quality state must also be per metric, not one quality value for the whole record: a structured zero for `running` must not prevent a later structured `failed` value from filling that different field, and a lower-quality fallback for one field must not block or overwrite another field.
- Treat a present structured metric as authoritative even when it is malformed. Carry malformed/present state per metric, keep that metric unavailable with a warning/partial marker, and suppress lower-quality visible-text or ARIA fallback for the same metric. A trailing-garbage JSON count or malformed structured edge count must not turn into a confident value merely because a fallback label is available; independent fields may still be filled when their own sources are valid.
- Presence-aware booleans require three-way handling: recognized true, recognized false, and unknown/malformed. An unrecognized freshness/status value must remain unavailable and partial, not silently become `false` and render as `fresh` or another confident state. An explicitly present but invalid status/freshness attribute also suppresses derived prose fallback; only derive a status from text when no structured status attribute was present.
- Treat response identity and project scope as invariants: validate the automation and project markers when present and reject a response that identifies another resource or project. Parse nested structured attributes and compact state/count labels, normalize backend enum labels for terminal readability, and sort node/edge/resource rows by stable identifiers for deterministic output.
- Join and de-duplicate graph records only with stable IDs, node keys, or verified endpoint identity. Human labels are not unique: never collapse separate edges because their labels match, and never drop a count-only edge merely because the fragment lacks an ID. If the markup lacks enough identity to correlate a detail record, do not guess or create a duplicate topology row; preserve the authoritative record and surface the correlation as unavailable or a warning.
- Resource-row identity must include every backend-distinguishing key, including the owning node identity, resource type, resource ID, and relation. The backend can legitimately retain rows that differ only by relation (`owned`, `shared`, `input`, or `output`); never de-duplicate those rows using a key that omits relation, and never treat an empty optional display name as proof that the resource is duplicate.
- Keep semantic runtime states independent from CSS presentation classes. A generic visual class such as `--completed` may represent a more specific state such as `recently_completed`; prefer explicit data attributes or the backend's canonical enum, map backend `completed`/recent markers to the distinct terminal state when that is the contract, and add table-driven regressions for each state and fallback.
- Resolve `show`/`open` references through the existing list-first `matchRef` order: exact ID/name, unique prefix, then unique substring; reject unknown and ambiguous refs before issuing the detail request or any mutation. A missing interactive ref opens the existing selector, while CLI mode returns usage without a selector. If a selector already fetched the candidates, carry the canonical selected record/ref into dispatch instead of listing again.
- Require a selected project before parsing the action or opening a selector. For a resolved automation, the normal request sequence is one project-scoped list request followed by exactly one `GET /automations/:id?project_id=<selected>` detail request. Add request-count assertions and verify that no detail request or mutation occurs after resolution failure.
- Distinguish a draft/no-live-graph response, an empty graph, a not-found detail, a backend error, and a malformed or partial fragment. A draft listed automation may use explicit list metadata as a fallback when the detail route reports no live graph, but must say that no live graph was loaded. Do not render graph rows or claim counts when the graph section is absent.
- When graph nodes and a node-details panel are both present, correlate details only by stable node ID/key and preserve graph rows as authoritative when correlation fails. When the graph section is absent but a valid node-details section is present, treat that section as the authoritative detail-only topology and retain every distinct detail record; do not append only the first record and then discard later records as “uncorrelated.” If identity is insufficient, retain the record with an unavailable/correlation warning rather than guessing or dropping it. When both representations are present, an unmatched detail record must likewise remain visible as a separate detail-only record or equivalent partial record; warning and retaining it is safer than silently dropping data.
- Keep plain rendering compact and stable, with explicit sections for identity, graph, runtime, resources, and external state. If JSON is supported, marshal a tagged detail model as bare machine-readable JSON with no ANSI styling, banner, or terminal-only text.
- Treat every backend-controlled string that reaches interactive or plain terminal rendering as hostile input. Strip ANSI escape sequences and other terminal control characters at the presentation boundary before writing names, IDs, metadata, labels, resource fields, and warnings into headings, table cells, or CLI output. Keep JSON values semantically intact when JSON is the contract, and test hostile values through both the renderer and headless output; absence of renderer-added ANSI is not evidence that backend text is safe.

## Audit Hardening

- Never correlate graph and detail edge records by document order, source representation, or a shared label alone. Merge only on a shared stable edge ID/key or a complete, verified endpoint identity that is unique in the response; when identity is insufficient, retain the source records independently and emit an unavailable/correlation warning rather than attaching one record's counts or topology to another. Parse and collect both complete representations before evaluating endpoint uniqueness; an incremental merge can accept an early duplicate and cannot be safely undone when a later duplicate appears.
- Keep correlation-unavailable edge records separate from authoritative graph topology in both the data model and the renderer. For example, when the backend SVG exposes one count-bearing edge without identity while the detail panel exposes one key-bearing endpoint record, do not append both to the authoritative edge list or report their combined length as the graph's edge count. Render the authoritative graph row once and place retained count-only/detail-only evidence in an explicitly labelled unmatched or diagnostic section, preserving warnings and per-record availability rather than making one GUI edge look like two.
- Apply per-field provenance to edge metrics just as to node metrics. A structured transition or recent-transition count outranks an ARIA/visible-text fallback independently for each metric, and an explicit structured zero must remain available. Merging one edge record must not let an already-present lower-quality value block a higher-quality value for either metric.
- If a structured edge metric is present but invalid, mark only that metric malformed/unavailable and do not recover it from the edge's ARIA label or visible text. Preserve valid independent metrics and keep the warning/partial state.
- Treat every explicit presence boolean as tri-state. A present value is not automatically recognized: parse only an allowlisted true/false vocabulary, preserve unknown or malformed values as unavailable, add a warning/partial marker, and do not let a generic visible-text fallback override an explicit invalid attribute. This applies to graph availability and external freshness/status as well as per-record fields.
- Keep textual freshness parsing exact and polarity-safe. Do not infer `fresh` or `stale` from an arbitrary substring such as `not fresh`; normalize and accept only the documented positive labels or boolean tokens, leaving negated, qualified, unknown, and malformed text such as `maybe stale`, `not fresh`, or `not currently stale` unavailable and warned. Do not derive a status from freshness prose after an explicit structured status was present but invalid.
- Parse structured optional count payloads strictly. After decoding the expected JSON object, require end-of-input; a valid object followed by trailing garbage is malformed. Textual count extraction must enforce numeric boundaries and reject a negative sign rather than converting `-2` to the positive magnitude. Require an actual separator or approved punctuation between a textual label and its number in either direction; reject concatenated forms such as `running2` and `2running`, trailing words, decimals, and other malformed tokens. Malformed values stay unavailable and make the detail partial.
- Deterministic rendering must sort resources by the complete stable identity, including node identity, resource type, resource ID, and relation, with deterministic display-field tie-breakers when necessary. Relation is both a de-duplication key and a sort key; omitting it can make valid relation-distinct rows reorder unpredictably.
- Audit terminal safety independently from styling. A plain renderer can avoid adding ANSI while still replaying escape sequences supplied by the backend; inject control characters into every displayed field class and assert that interactive and CLI plain output contains no terminal controls while JSON remains valid and intentionally preserves its data contract.

## Regression Workflow Notes

- After a surgical edit to an `_test.go` file, compile the affected test package immediately with a focused `go test` or a no-run test command such as `go test ./internal/client -run '^$'`. `go build ./...` does not compile test files and can miss malformed test declarations before implementation work proceeds.
- Preserve structured invalidity beyond an empty value when data crosses the parser-to-renderer boundary. An explicit invalid-status marker or equivalent presence state prevents the renderer from reinterpreting a missing status as a confident freshness value.
- When graph and detail records cannot be correlated, retain every marked detail record, including one with no recoverable ID, key, or name, in a separate detail-only collection. Render an explicit correlation-unavailable note so authoritative graph counts stay accurate without silently losing configuration data.
- Parse all candidate freshness lines before accepting a result. A later qualified, contradictory, or ambiguous line must invalidate an earlier positive token rather than allowing document order to produce a confident state.
- Add a regression using the actual backend fragment shape where SVG edges lack IDs/endpoints and detail edges carry keys/endpoints. Assert one authoritative graph edge, a separate unmatched diagnostic record or section, an explicit correlation warning, and no inflated graph cardinality in plain or JSON output.

## Fixtures And Validation

- Mirror valid backend markup in parser fixtures. In particular, `golang.org/x/net/html` reparses invalid direct children inside `<svg>`; SVG graph labels and counts should use the same valid `<foreignObject>` structure as the generated backend template, or the fixture can produce misleading missing names/counts unrelated to the client logic.
- Add focused parser and renderer regressions for mixed per-field availability, explicit zeroes, structured-versus-text contradictions, malformed structured values with fallback text/ARIA present, per-field provenance (including a structured value arriving after a fallback value for a different field), unknown/malformed freshness and status values, explicit invalid status plus stale/fresh prose, qualified or negated freshness text, relation-distinct resource rows and relation-sensitive ordering, duplicate labels, unlabelled and count-only edges, unmatched identity, unmatched mixed graph/detail node records, detail-only sections with multiple nodes, semantic `recently_completed` state, and JSON preservation of availability flags.
- Also regression-test reordered graph/detail edges, same-label edges with different endpoints, explicit unknown graph availability, negated or unknown freshness text, higher-quality structured edge counts, malformed structured edge counts that must not fall back to ARIA, trailing JSON garbage, negative textual counts, concatenated label/number counts, and deterministic resource ordering under permuted input. These cases must prove that no topology or metric is silently reassigned, dropped, or converted into a confident value and that warnings/partial state are preserved.
- Add hostile backend text fixtures for automation names, IDs, metadata, graph labels, resource fields, and warnings. Verify that terminal renderers and plain CLI output remove ANSI/control sequences without changing the valid JSON schema or silently dropping intended JSON data.

Regression coverage should include a selected-project detail request with the expected query scope, one-request list/detail sequencing, no-project guard with zero HTTP requests, exact/name/prefix/substring/unknown/ambiguous resolution, missing-ref selector behavior in TUI mode, the original usage error in CLI mode, selector request reuse, and rendering of representative node/edge, live-status, resource, and external-state fields. Also cover the actual backend fragment's omitted optional sections separately from synthetic complete fixtures; published, draft/no-live-graph, empty graph, not-found, backend error, malformed fragment, partial per-section and per-record values, duplicate edge labels, count-only edges, semantic `recently_completed` state, JSON validity, relation-distinct resources, detail-only multi-record topology, hostile terminal text, and preservation of existing lifecycle/list behavior. Finish with `gofmt`, `go build ./...`, `go vet ./...`, and `go test ./...`.
