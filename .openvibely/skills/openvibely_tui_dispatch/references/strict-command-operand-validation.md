# Strict Command Operand Validation

Use this reference when a registry command must reject unknown actions or surplus operands consistently in both interactive and one-shot CLI dispatch.

- Express the accepted grammar as a command-level argument validator when both dispatch modes need the same rule. Accept documented default forms and intentional missing-reference forms that open an interactive selector; reject unknown actions and extra operands with canonical registry-backed usage.
- In `RunCLIContext`, invoke the command validator immediately after command lookup and before model creation, project loading, preflight, status checks, streaming dispatch, or any backend request. Return its error directly so malformed input exits nonzero and cannot trigger even read-only setup requests.
- In the interactive command handler, preserve established higher-priority local guards such as `needProject()`, then invoke the same validator before `splitAction`, resource matching, selector setup, confirmation setup, or backend work. This keeps no-project guidance precedence while ensuring malformed selected-project commands have no side effects.
- Keep action syntax and runtime errors coupled through `commandActionUsage` and `commandUsage`; include a command-level empty-action usage entry when an unknown action needs the complete accepted grammar. Do not duplicate usage literals in validation and help.
- Add table-driven tests for unknown actions and surplus operands on every action. Interactive tests should assert canonical usage, zero requests, and inactive selector/confirmation state. CLI tests should assert a non-nil error containing prefix-appropriate canonical usage and zero requests, including no project-list request. Also retain positive tests for the bare/default form, explicit list form, missing-reference selector behavior, project scoping, destructive confirmation/`--force`, and transport aliases such as Slack `remove` mapping to `disconnect`.
- During a strictly read-only audit, inspect command/handler ordering and request-count assertions rather than rerunning modifying validation commands. Confirm the worktree remains clean and rely on separately recorded build, vet, and test evidence when the lifecycle explicitly requires audit-only behavior.
