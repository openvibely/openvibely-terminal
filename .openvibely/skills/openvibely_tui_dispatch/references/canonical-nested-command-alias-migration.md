# Canonical Nested Command And Deprecated Alias Migration

Use this reference when moving an existing top-level command under a canonical parent command while retaining compatibility aliases.

- Choose one canonical registry-backed hierarchy and route every legacy spelling into the same dispatcher. Do not fork handlers, selector logic, project scoping, client calls, confirmation paths, errors, or completion metadata between canonical and alias forms.
- Keep compatibility aliases only when removal would break existing users. Mark them deprecated in documentation, hide them from top-level discovery and suggestions when possible, but keep direct dispatch working. Advertise only the canonical hierarchy in primary help, examples, selector-prefilled commands, and runtime usage text.
- Generate deep action and option completion from shared metadata for both canonical and accepted alias paths. Test action completion and create/edit option completion so nested paths and aliases cannot drift.
- Preserve exact free-form references, including names that resemble options. Run operand and option validation before project discovery, selector fetches, confirmation setup, or mutation; malformed canonical and alias invocations must make zero requests.
- If selector discovery already resolved the selected record, carry that canonical record or reference into show, test, rotate, and delete dispatch rather than repeating the same list request. Keep edit as a prefill path when it still needs user-supplied options. Add ordered request-count assertions.
- When a subtype shares a backend collection with its parent, define mutually clear views. Filter subtype records from the parent's ordinary list and expose them only in the subtype list, while preserving subtype pagination. Avoid traversing subtype-only continuation pages from the filtered parent list when one page is sufficient for the parent contract.
- Add parity tests that run canonical and alias forms against equivalent fixtures and compare request sequences, query scoping, output, errors, selector behavior, confirmations, and completion. Also assert aliases remain dispatchable but do not create duplicate visible command entries.
- Retain the established security and mutation tests through the shared dispatcher: no secret values in transcript, errors, or diagnostics; no mutation before validation and confirmation; cancellation makes no mutation; destructive CLI actions retain force requirements; terminal output remains safe.
- Update the README command table, detailed help, examples, option reference, destructive behavior, and deprecation note together. Verify the final surface with focused registry/client/TUI tests, then run `go build ./...`, `go vet ./...`, uncached `go test ./...`, race tests when applicable, formatting checks, and `git diff --check`.
