# Lifecycle Execution Response Contract

Use this checklist when changing `/tasks lifecycle` execution-list behavior across `internal/client` and `internal/tui`:

- Inspect the current backend handler and generated Swagger before changing fixtures. The authoritative lifecycle-execution list response is an object envelope: `{"items":[...],"has_more":false,"next_cursor":"..."}`. Do not model the endpoint as a bare `[]LifecycleExecution` or treat backend `null` as an empty list.
- If compatibility is required, support only shapes proven by backend or first-party client evidence. The backend web client provides evidence for a legacy top-level array, so decode exactly the current envelope and that legacy array. Reject `null`, unrelated objects, missing or non-array `items`, malformed metadata, trailing JSON, and `null`/non-object execution entries.
- Represent the page as a client contract rather than flattening immediately. Keep `items`, `has_more`, and `next_cursor` available to plain rendering and preserve the validated top-level shape, including unknown forward-compatible metadata, for `--json`; do not use permissive maps or a decoder that hides schema drift.
- Treat operand presence, not response cardinality, as the intent boundary. A task-only `/tasks lifecycle <task>` request renders or serializes the execution page when it has zero, one, or many items. Fetch and render `/api/lifecycle-executions/<execution>/events` only when the user explicitly supplies an execution reference; never auto-drill into a sole execution.
- In interactive mode, task-only pages with multiple executions may open the execution selector, while zero- and one-item pages render directly. Headless CLI task-only behavior stays deterministic by rendering the page for every cardinality. Explicit `<task> <execution>` requests retain event-trace behavior.
- Keep compatibility wrappers for existing slice consumers only when needed, and normalize a valid empty collection to a non-nil slice there. Do not let those wrappers redefine the endpoint's raw JSON contract.
- Interactive `/tasks lifecycle` with no task ref must use the normal task selector. Account for selector auto-dispatch when a fixture has only one task; use multiple candidates when a test must assert that the selector remains visible.
- Plain output must render an explicit empty state and expose continuation metadata when supplied. Sanitize every server-controlled heading, label, cursor, status/time cell, and preview before terminal output; bound previews and test truncation rather than asserting unbounded injected text.
- Preserve selected-project `project_id` on execution-list and explicit event-trace requests, direct full-ID resolution, authentication/API error classification, context cancellation, and existing event behavior.
- Add realistic regressions for populated, one-item, and empty envelopes; legacy arrays if still supported; malformed top-level/member shapes; `null` entries; trailing JSON; HTTP/auth failures; selector and typed-ref flows; metadata; complete `--json`; terminal-safe bounded output; and zero implicit event requests for task-only one-item responses. Existing event-order tests should supply an explicit execution reference.
- Validate transport changes with focused tests followed by `go build ./...`, `go test ./... -count=1`, `go vet ./...`, `gofmt -l`, and `git diff --check`. JSON shape normalization alone does not require the race detector; add a focused `-race` invocation only if concurrent lifecycle loading or shared state also changes.
