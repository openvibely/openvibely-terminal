Use this skill for Native SDLC vision-suggestion audits where the repository must be compared with its product vision and any new gap reported as an automation notification.

## Procedure

- Check for a root `VISION.md` first and read it before choosing an area. Select one focused, user-visible component or workflow, vary the area between runs, and keep the audit read-only: do not modify code or create implementation tasks. Do not use GitHub issues for duplicate detection.
- Trace the complete user path and compare expected behavior with implementation, tests, documentation, configuration, and CI source-of-truth files. For CLI/TUI workflows, exercise representative generated help or registry output and compare it with README or quickstart command tables so stale documentation is caught as a contract gap. For any command that calls a backend, verify the advertised route against the current backend route registration and Swagger or handler source, not only the client method or a local mock. Inspect `httptest` fixtures for synthetic routes because tests that accept a removed endpoint can mask a real 404. For Go install/toolchain audits, compare README claims with `go.mod` `go`/`toolchain` directives and CI's selected toolchain; run `go build ./...` and `go test ./...` on the declared toolchain so a passing runtime does not hide an install-contract mismatch. For platform-support audits, distinguish successful cross-compilation from an actual release, artifact, or install workflow by inspecting CI and packaging configuration.
- For first-run or backend-connection audits, trace connection-refused startup, offline recovery text, URL configuration, command discovery, help, and setup documentation as one journey. Compare any “start or check the backend” instruction with the actual platform-specific installer or distribution paths in the backend source of truth. Treat a dead-end message with no discoverable setup or health-verification path as a concrete browser-free workflow gap, while distinguishing an explicit guided setup command from unsafe automatic installation. Test malformed configured server URLs as a separate branch: preserve whether the user intended a remote address through parse failure, and require configuration-correction guidance rather than local-offline setup instructions; reproduce both default-local and configured-remote cases.
- For post-selection onboarding audits, trace automatic startup selection, explicit selection, and project creation through the transcript output, empty-state guidance, command registry, generated help, and documentation. Compare static advice with existing read-only status, approval, active-work, and upcoming-work signals; if users must already know hidden commands to discover what needs attention, treat the lack of state-aware next actions as a distinct guidance gap rather than a missing backend capability.
- For resource-management workflows, compare the backend's full supported lifecycle with terminal commands and client methods, including create, inspect, update, select/default, and delete operations. For project creation specifically, inventory every backend- and web-supported repository source or import mode, such as local paths and hosted repository URLs, and verify that the terminal exposes equivalent inputs, sends the correct source discriminator and metadata, and documents the workflow. For connected communication integrations, examine configuration and connectivity separately from inbound access control: inventory any project-scoped sender or user allowlist list/add/remove lifecycle for every supported channel, including providers omitted from the terminal's initial provider set, rather than treating configure/test support as feature parity. For outbound message destinations or saved targets, inspect the backend route/handler and web settings for the complete add, edit, delete, test, and default/home-target or unsaved-target-policy lifecycle, then compare it with terminal registry entries, client resources, generated help, tests, and documentation. Treat backend- or web-supported outbound-target management with no terminal-native equivalent as a separate browser-free feature-parity gap, even when inbound channel access controls are already present.
- For capacity and quota status, trace backend sentinel values and derived fields through every user-facing renderer, not just the happy-path numeric calculation. Verify that values such as zero meaning unlimited, unknown, disabled, or unavailable are displayed with their documented semantic meaning and do not produce misleading values such as an exhausted zero-capacity pool; compare related commands that may already render the sentinel correctly and add focused regression coverage for each semantic branch.
- For task-goal workflows, enumerate state-transition controls as well as configuration: compare set/clear and every backend-supported action such as pause/resume against terminal registration, client methods, generated help, tests, and documentation. Verify that all goal mutations carry the active selected-project context, including the newly exposed lifecycle actions, so interactive and scripted use cannot silently affect an unintended project.
- For task-response workflows, inspect the active-response lifecycle separately from ordinary follow-up replies: enumerate backend controls for steering or interrupting an in-flight response, inspecting or canceling pending input, and steering queued input; compare route registration, client methods, terminal registry/actions, generated help, documentation, and regressions. Treat backend or web support for these controls without terminal-native equivalents as a browser-free feature-parity gap, and verify active-response/concurrency guards plus stale-task or no-pending-input behavior before filing.
- For analytics and reporting workflows, inventory every independently supported backend section from route registration, Swagger, handlers, and the web dashboard, then compare that inventory with the terminal command registry, client methods, renderers, generated help, tests, and documentation. Treat a backend- or web-supported section absent from the terminal as a feature-parity gap only after confirming the route is real rather than synthetic test data. For aggregate commands that fetch independent sections, inspect degraded-dependency behavior separately: a failed section should not be silently dropped while the command reports success, and healthy sections should remain visible with an explicit partial-failure signal when the contract permits.
- For status, diagnostics, and recovery workflows that advertise multiple independent signals, inspect command preflight and dependency ordering separately from each individual check. Verify that failure of an optional or project-scoped endpoint does not suppress global health, authentication, capacity, or other independently available output; reproduce degraded-dependency cases with focused fixtures and compare the actual exit status and rendered output with the documented contract. Treat generic preflight blocking and missing partial results as a distinct user-visible gap only when the behavior is independently actionable and not already covered.
- For alert or approval workflow audits, compare the web and terminal paths end to end: list query parameters and bounded-page behavior, decision/processing-state filters, stable notification IDs, full body/metadata detail retrieval, and links to implementation tasks. Verify that terminal filtering forwards every relevant backend-supported exact workflow-state filter, including a combined set where supported, rather than applying a loose local text match to a broad downloaded list; test filtered paging and project scope so unrelated alerts cannot appear as review candidates. Confirm that a terminal user can inspect the same rationale and structured context needed for an approval before acting. Check generated `help alerts` and read-only output in addition to the list model; when the backend separates list and detail routes, treat a missing detail path as a workflow-parity gap rather than assuming the list response is complete. Compare action scope too: verify whether the terminal exposes every backend-supported safe scope, including one alert, all matching alerts, and a user-selected set of several alerts. A terminal that offers only one-or-all actions despite backend support for selected IDs has a review-efficiency gap; retain confirmations for destructive bulk actions.
- For bounded alert/card lists, inspect the pagination signal itself, such as `X-OpenVibely-Card-Page-Has-More` or `data-card-pagination-has-more`, and trace it through the client model, renderer, filtering, and action lookup. A client that discards page metadata or applies only a local filter to the first page cannot find older pending alerts or reliably resolve them; verify the missing-page path with a fixture that places a target record beyond the first page.
- Before filing anything, paginate `list_existing_automation_notifications` until `next_offset` is zero. Compare notification IDs, titles, types, and lifecycle states; for plausible matches, call `get_alert` and read the body. Treat a finding as covered when the existing alert represents the same user problem or implementation scope. If an existing alert covers only other providers or explicitly excludes the provider under audit, do not treat that scope statement as coverage; read the body and preserve the narrower candidate when it is independently actionable. If a broad candidate is covered, continue only if a narrower, independently actionable gap remains; otherwise pivot to another user-visible workflow or vision area rather than restating the finding, and restart evidence and duplicate checks for that candidate. Create at most one notification per run.
- Create a new notification only after the full duplicate review, using type `product_suggestion`. The body must begin with exactly `## Summary`, followed by 2-4 plain-language sentences stating the problem, one concrete user-visible example, and why it matters. Put technical detail after the summary: inspected component, evidence and failure paths, expected versus actual behavior, risk, implementation direction, acceptance criteria, relevant files or symbols, and regression cases.
- Before reporting completion, run applicable read-only validation for the inspected surface. For Go/TUI audits, use the relevant generated-help check plus `go build ./...`, `go test ./...`, `go vet ./...`, and `git diff --check` when applicable; report the exact commands and any failures rather than implying the finding was validated. Confirm the worktree remains unchanged after the audit with `git status --short`. If a strict read-only audit boundary also applies, do not run builds, tests, generated-help commands, or any command that may write caches or artifacts; rely on source inspection and report that those validations were intentionally not run.
- Report that the suggestion is pending human review: approval authorizes task creation only, not merge, release, or deployment. State that no code or implementation tasks were changed and include validation commands/results and any related alert that was confirmed distinct.

## Pitfalls

- Do not stop duplicate scanning at the first page or compare titles alone; an apparently different title can cover the same fix, while a completed alert may still explain the scope.
- Do not force a covered candidate into a notification. Pivot to a distinct workflow only when its evidence and user impact are independently actionable, and apply the full duplicate scan again.
- Do not infer terminal feature parity from read-only listing or deletion support; enumerate the backend lifecycle and verify whether users can create and edit the resource without leaving the terminal.
- Do not assume a command's declared scope or individual checks make them independent: trace CLI preflight before the handler and test healthy global endpoints with a failing project-scoped endpoint; a nonzero generic error that suppresses advertised status output can be a distinct user-visible contract gap.
- Do not treat generated help and README command tables as interchangeable sources; verify both because either can drift.
- Do not treat a client-side route or synthetic test server as proof that the backend supports an endpoint; check the backend's registered route table and Swagger or handler source, and treat a 404 contract mismatch as a user-visible finding when it is not already covered.
- Do not treat cross-compilation as proof that users can obtain or install a supported platform release; verify artifact and distribution paths separately.
- Do not turn a current repository fact such as a specific version mismatch into a permanent rule. Preserve the repeatable comparison and validation method instead.
- Do not put implementation detail before the user-facing summary, and do not report a passing build as proof that documentation or installation guidance is correct.
