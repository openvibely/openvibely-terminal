# Strict Read-Only Implementation Audit

Use this skill when a task requires a separate audit-only turn after implementation or fixes.

## Audit Boundary

- Treat the entire workspace as immutable. Inspect and report only; do not edit, patch, format, generate files, update dependencies, create commits, or run commands that may write caches or artifacts.
- Safe inspection normally includes file reads and read-only Git operations such as `git status`, `git diff`, `git show`, and `git log`. Before running any other command, determine whether it can write to the repository, tool caches, temporary outputs, generated files, lockfiles, or external state.
- Do not run builds, tests, benchmarks, formatters, code generators, package installers, or fix modes during the audit. Review recorded validation evidence from the implementation turn instead. If required evidence is absent or stale, report that as a finding rather than generating it.
- Treat validation as recorded only when the audit can identify the command outcome and the exact covered commit from available source evidence. Do not infer it from a clean tree, source tests, commit position or diff, memory, or a prior assistant assertion. If that evidence is unavailable, say validation could not be independently verified instead of claiming the current HEAD was covered.
- Memory and skill reads may provide context, but base the verdict on the implementation, workspace, requirements, and validation evidence. Do not report memory or skill drift as an implementation finding.

## Review Procedure

1. Confirm the intended checkout, branch or commit, and workspace status using read-only inspection.
2. Identify the implementation diff and map each requirement to changed code, tests, and previously recorded validation evidence. Validation must apply to the exact audited HEAD; treat evidence from before a merge, rebase, conflict resolution, or later commit as stale unless equivalence is established.
3. Trace affected control flow and edge cases from source. Check output compatibility, error behavior, filtering or scoping, cancellation, and fallback paths relevant to the change.
4. For HTML/HTMX actions, inspect response-body semantics as well as status codes. A backend may return HTTP 2xx for both success and failure fragments and encode the verdict in semantic markup such as error/success classes or structured attributes; verify the client parses that distinction and add realistic regressions for both bodies.
5. Audit each user-facing action against the backend's exact per-resource operation rather than assuming aliases are interchangeable. Distinguish disconnecting runtime/OAuth state from deleting configuration, and verify unsupported resource/action combinations fail before confirmation or requests.
6. For paginated or enveloped responses, audit zero-item, singleton, and multi-item branches independently. Cardinality-based auto-selection or drill-down must not discard page metadata, future fields, raw JSON shape, or continuation state; require explicit selection when the command contract distinguishes listing a page from showing one item's detail.
7. When one resource family is removed from a mixed HTML page or command surface, inspect the full semantic ancestor, not only individual cards. Verify headings, empty-state copy, controls, pagination chrome, and explanatory text for the removed family are also absent, while unrelated resource sections remain. Require a realistic regression that asserts both absence of all removed-family residue and preservation of the retained family.
8. For destructive or irreversible workflows, verify the target reference is resolved, authorized, and canonicalized before the confirmation prompt. Invalid or ambiguous references should fail without prompting, and the prompt should name the exact canonical target that the confirmed action will affect. Require regressions for ambiguous, unknown, partial-but-unique, and canonical references.
9. For full-replacement edit APIs, compare every fetched field and submitted form key with the authoritative backend handler and model. Validate user-editable values locally when the backend normalizes invalid input, so typos cannot silently persist a fallback. Verify reference matching keeps ID, name, and alternate key as separate exact-match candidates rather than concatenating them. Require fresh post-save state for machine-readable success output and preserve partial refresh failures, but classify typed authentication and transport errors before generic saved-with-refresh-error handling so success reporting cannot suppress required recovery guidance. Assert raw plain output rejects ANSI, control, newline, and carriage-return injection.
10. For commands where option markers or separators may also be valid operand text, enumerate every plausible parse boundary before selecting a target. A separator fast path must compete with literal-value and longer-reference interpretations under the same ranking and ambiguity rules; it must not return early merely because one prefix resolves. Require collision regressions with multiple real resources that prove malformed or ambiguous input performs no detail or mutation request and cannot shorten or rebind the target.
11. For cleanup, invalidation, reset, cancellation, or error-transition changes, inspect the shared helper and every caller rather than only the patched path. Verify buffered data is flushed or deliberately retained before timers, streams, projects, sessions, or scopes are invalidated. Treat scheduled timers as independent in-flight messages, and require regressions for stale timer delivery after a forced flush or ownership change. For multi-stage operations such as preview-then-save, exercise cancellation independently after every network stage has started, especially the persistence stage; proving only the preview request is canceled does not establish that teardown can stop an already-started mutation.
12. For asynchronous state, verify stale results are rejected before any state mutation. Cover project and session transitions, overlapping submissions, completion events, reconnects, and cancellation boundaries that can reorder transcript or event output. Once an active turn has a correlation identity, treat identity-less same-scope events as unproven rather than compatible: test them both before and after acknowledgement, and ensure they cannot change status, append duplicate output, or settle the turn. When terminal status reconciles streamed output, do not assume its response snapshot is complete or newer: verify empty and shorter/lagging snapshots cannot erase or regress already accepted bytes, and require focused no-loss regressions.
13. For transport-owned resources, assume `Close` can race with lazy `Open`, cancellation, or framework cleanup. Verify synchronization, cleanup-error propagation, waiter ordering, and compatibility of public error types and ordering. Treat metadata-to-open gaps as TOCTOU boundaries when metadata controls lengths, limits, or payload semantics.
14. For bounded JSON preview or serializer changes, load the companion `bounded_json_preview` skill and apply its semantic, adversarial, and allocation checks. In the audit verdict, specifically verify that bounds cover concrete fast paths and reflected paths, late errors and cycles remain detectable after the visible prefix fills, custom marshalers preserve invocation and ordering semantics, and tests compare against `encoding/json` rather than only happy-path fixtures.
15. Treat every rendered error string as untrusted terminal data, including client transport errors. Audit diagnostic wrappers, stored connection errors, status views, footer hints, and CLI/startup error wrappers together: transport errors may embed the complete configured request URL, while HTTP/backend errors may contain arbitrary response text, and a reachable configured-login failure can leak a raw `BaseURL` even when its backend error is generic. Redact URL userinfo, query parameters, fragments, and complete header-style credential values before rendering; `Authorization: Basic <base64>` and `Authorization: Bearer <token>` must redact both scheme and payload, not merely a key/value token. Strip terminal controls and collapse layout-breaking whitespace from remaining diagnostics. Do not assume URL schemes are lowercase when matching embedded URLs: use case-insensitive scheme recognition or parser-based redaction, then test lowercase, uppercase, and mixed-case `HTTP(S)` URLs carrying userinfo, query secrets, and fragments. For combined connection states, retain sign-in-required precedence after a later transport failure without regressing remote recovery: an explicitly configured remote endpoint must still advise checking or correcting that remote URL, never local-start guidance, in both `/status` and the persistent hint. Require a regression for auth-required plus a remote transport failure and raw-output regressions using an authenticated/query-bearing request URL, a Basic authorization value, and ANSI/control/newline-bearing backend error text, rather than only synthetic harmless errors. Assert status diagnostics on the raw rendered string before stripping renderer-owned ANSI; a raw configured-URL sentinel alone does not cover controls originating in the diagnostic.
16. Review tests for meaningful regression coverage rather than merely counting added cases. Verify each assertion observes the value before any helper normalizes away the defect. For terminal-safety tests, assert injected ANSI/control sequences are absent from raw rendered output before using helpers such as `stripANSI` for readability checks.
17. Distinguish multiline content from single-line metadata when reviewing terminal sanitization. A sanitizer that correctly preserves newlines for document bodies is unsafe for titles, paths, statuses, confirmation fields, or other layout-bearing values unless those separators are collapsed or rejected. Exercise `\\n` and `\\r` injection as well as ANSI escapes, bells, tabs, and other controls, and assert the raw output retains its intended line structure.
18. Report every material bug, regression, missing requirement, or missing required validation. Do not fix findings in the audit turn.
19. If no material issue remains, explicitly state that the fresh strictly read-only audit found none.

## Follow-Up Discipline

- Fixes belong in a separate implementation turn. After fixes, stop and require a fresh audit-only review from scratch.
- An audit that edits files or runs a modifying command is invalid and must not be used as the clean final review.
