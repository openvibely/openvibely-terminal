# Strict Read-Only Implementation Audit

Use this skill when a task requires a separate audit-only turn after implementation or fixes.

## Audit Boundary

- Treat the entire workspace as immutable. Inspect and report only; do not edit, patch, format, generate files, update dependencies, create commits, or run commands that may write caches or artifacts.
- Safe inspection normally includes file reads and read-only Git operations such as `git status`, `git diff`, `git show`, and `git log`. Before running any other command, determine whether it can write to the repository, tool caches, temporary outputs, generated files, lockfiles, or external state. Treat shell redirection and temporary-file creation as mutations even outside the repository. Do not use `\u003e`, `\u003e\u003e`, `tee`, heredoc/file-producing commands such as `cat \u003e /tmp/...`, `mktemp`, `touch`, or ad hoc scripts/probes such as `go run` that require a generated file. Do not run a command unless its complete pipeline, substitution, and redirections are read-only; when uncertain, use file-read/search tools or omit the check.
- Do not run builds, tests, benchmarks, formatters, code generators, package installers, fix modes, or ad hoc diagnostic programs during the audit. Review recorded validation evidence from the implementation turn instead. If required evidence is absent or stale, report that as a finding rather than generating it.
- If any audit action writes a file, cache, artifact, temporary output, repository state, memory, or skill configuration, the audit is invalid. Do not issue a clean verdict; report the boundary violation and require a fresh audit from scratch after the workspace is restored.
- Treat validation as recorded only when the audit can identify the command outcome and the exact covered commit from available source evidence. If that evidence is unavailable, say validation could not be independently verified instead of claiming the current HEAD was covered.
- When validation ran before the implementation was committed, explicitly establish that its post-format patch is the audited commit with read-only evidence, such as comparing the recorded final diff with `git diff HEAD^ HEAD` and confirming no intervening source changes. A claim that the patch was identical is not sufficient; otherwise report exact-HEAD validation as unavailable.
- Do not infer exact-HEAD coverage from a clean worktree, matching changed paths or line counts, reflog timestamps, commit messages, or a narrative that the patch was identical. Unless a durable validation record contains the command outcomes and commit or a recorded source diff can be compared byte-for-byte to `git diff HEAD^ HEAD` with no intervening source changes, report exact-HEAD validation as unavailable and do not issue a clean verdict on validation completeness.
- Treat opaque aggregate validation logs or malformed combined pipelines as insufficient evidence for individual gates. Require focused tests, build, vet, full tests, formatting, and diff checks to have independently identifiable outcomes, and require a durable record attached to and read back from the exact audited commit; a clean worktree or one `tee` transcript cannot substitute for those checks.
- Memory and skill reads may provide context, but base the verdict on the implementation, workspace, requirements, and validation evidence. Do not report memory or skill drift as an implementation finding.
- For project-scoped HTML/HTMX authorization or access-list rows, treat a route `project_id` query as request scope only, not proof of row ownership. Require an explicit persisted row/project ownership marker backed by the server contract on every parsed row, reject missing markers as well as malformed or foreign markers, and do not let a valid page-level form marker substitute for row-level ownership evidence. Re-list or revalidate ownership immediately before destructive deletion.
- For row-level HTML/HTMX authorization evidence, “on every parsed row” means the exact persisted markers must be direct attributes of that row node, not values inherited by walking through children, controls, or ancestor wrappers. Accept only the exact marker names emitted by the verified backend contract; reject alias-only or compatibility marker names that the backend does not emit, duplicate marker names, and conflicting same-row markers. Add regressions for ancestor-inherited and alias-only evidence so a valid page marker or delete-control scope cannot accidentally become row ownership proof.
- When a client newly requires or strengthens row-level ownership metadata, inspect the designated backend templates or response builders at the relevant integration/default ref and verify that the exact persisted marker is emitted on every supported row. A page-level form marker or server-side filtering alone is not enough; if the real backend omits the marker, report the fail-closed client/backend contract mismatch as an integration defect rather than weakening the ownership check.
- When parsing structured HTML/HTMX fragments, compare client parser preconditions with the backend schema and every template branch. Optional presentation fields such as display names or labels must not make an otherwise valid identity row disappear; require the canonical identity and mutation control, retain rows when optional labels are empty, and inspect list and destructive-resolution behavior separately. Add regressions for empty optional fields as well as populated fields.

## Review Procedure

1. Confirm the intended checkout, branch or commit, and workspace status using read-only inspection.
2. Identify the implementation diff and map each requirement to changed code, tests, documentation, and previously recorded validation evidence. Validation must apply to the exact audited HEAD; treat evidence from before a merge, rebase, conflict resolution, or later commit as stale unless equivalence is established. If exact-HEAD evidence is unavailable, treat it as a validation handoff rather than rerunning checks in the audit: the separate non-audit continuation must use `exact_head_validation_evidence` to validate and durably record the final target commit before a fresh audit.
3. When a client change depends on a separately delivered backend contract, audit both repositories and delivery refs. Confirm the backend commit is reachable from the designated integration, release, or default branch used by the client, not merely a clean dedicated task branch; confirm the client’s expected deployment/runtime can consume that revision. Reconcile this conclusion with the direct command output: if an ancestry or reachability check is negative or contradicts memory or prior narrative, treat the direct result as authoritative, report the contract as unintegrated or delivery-blocked, and never claim reachability or a clean verdict without supporting evidence.
4. For performance or optimization tasks, load the relevant optimization-audit skill before judging the result. Map every numeric acceptance threshold to exact-HEAD evidence and require the benchmark to exercise the real scale-dependent cost. For aggregate status/count changes, constant-size synthetic responses labeled as different workload sizes do not prove collection-byte, end-to-end latency, or RSS thresholds; require matched realistic sizes such as 100, 1,000, and 5,000 cards, repeated median latency with controlled delays, response-byte totals against the baseline, and peak RSS or allocation measurements when those criteria are required.
   - When a collection parser is replaced by a compact server-side count, reconstruct the parser’s complete displayed-item semantics before accepting the new SQL or API predicates. Compare category/status filters, hidden categories such as chat or ordinary scheduled records, swarm-child or nested-card suppression, parent/task normalization, and any special inclusion rules for rendered columns. A database row being in the selected project is not proof that the old UI counted it. Require backend and client regressions for each hidden or specially normalized case, plus ordinary active, queued, empty, foreign-project, and partial-error cases.
5. Trace affected control flow and edge cases from source. Check output compatibility, error behavior, filtering or scoping, cancellation, and fallback paths relevant to the change. Treat user-facing documentation examples as executable interfaces: verify shell metacharacters and quoting preserve the intended argument boundaries, especially for pipes, redirects, command substitutions, chaining operators, and embedded quotes. A command shown in a shell block must be runnable as written or clearly marked as pseudocode.
   - When a refactor extracts a shared completion, refresh, or presentation helper, inspect every caller’s pre-helper setup and caller-supplied policy separately. Require regressions for each caller-specific resolution identity, output mode, success path, non-auth refresh failure, authentication failure, and status/fallback branch claimed by the requirements; coverage from one caller must not be treated as evidence for another.
   - For project-scoped destructive client actions, trace the selected project or tenant ID from project preflight and target resolution through interactive confirmation, forced/headless paths, the mutation query or form, and post-mutation refresh. Verify that no session-default fallback can change scope, and require exact-scope regressions for valid and foreign-project cases.
   - For destructive mutations followed by best-effort catalog refresh or backend selection recovery, keep the mutation result independent from optional redirect or selection-hint parsing and from the follow-up refresh. A malformed or unexpected selection hint must not turn an already completed mutation into a failed action or skip the required refresh; invalidate the deleted ID before applying any refresh result. If refresh is authentication-required, enter the normal auth-recovery state while retaining the successful mutation outcome; transport and reachable-backend refresh failures remain nonfatal diagnostics. Require regressions for malformed hints, auth-required refresh, and deleted-ID clearing.
   - When a parser changes option syntax to avoid a collision, audit the reverse collision as well: an equals-form or other newly reserved token may have been valid legacy positional text. Enumerate separated and attached forms, malformed and duplicate forms, literal option-looking paths, and pipe-delimited operands; verify the parser preserves the old local interpretation unless the new form is an explicit, unambiguous opt-in. Add regressions for each boundary, including URL-looking values and literal attached-option tokens both with and without a separator, not only after a pipe.
   - When a command completion value contains an attached assignment or delimiter-sensitive syntax such as `--option=`, trace the generic completion renderer’s token-boundary behavior. A completion string that looks correct in metadata can become an unusable command if the renderer appends whitespace and splits the intended token; verify the completed line tokenizes and dispatches to the same semantic path as the documented form, and add a regression that exercises execution rather than asserting only the rendered completion text.
6. For command-surface changes that add or extend a provider, resource, or action, compare canonical registry/action usage and generated help with completion metadata, README or user-guide tables/examples, and help/documentation regression tests. Search for stale allowlists or provider lists so users are not told a supported command is unavailable.
   - Verify every newly added provider or action appears consistently in command signatures, generated action usage, completion values, README examples, user-guide command tables/examples, and any generated or copied help blocks. Search for stale negative or out-of-scope statements that contradict the new capability, and ensure copied/generated documentation includes the new provider rather than only the implementation’s local help text.
   - After an action is renamed, split, or replaced, search the full documentation corpus for the old and new action tokens and inspect surrounding prose, not only code blocks or exact strings asserted by tests. In particular, verify nearby “same syntax,” CLI-equivalence, and follow-up instructions name the same action and route as the preceding example; a stale generic command such as `... create ...` can invalidate an otherwise correct dedicated action example.
   - When behavior depends on an environment or deployment constraint, treat generated help as a separate user-facing contract: it must explain the supported fallback or availability condition, not merely list the command. README or user-guide coverage does not substitute for the actual `help` output; require a help-specific assertion for the constraint and its actionable alternative.
7. For HTML/HTMX actions, inspect response-body semantics as well as status codes. A backend may return HTTP 2xx for both success and failure fragments and encode the verdict in semantic markup such as error/success classes or structured attributes; verify the client parses that distinction and add realistic regressions for both bodies.
8. Audit each user-facing action against the backend's exact per-resource operation rather than assuming aliases are interchangeable. Distinguish disconnecting runtime/OAuth state from deleting configuration, and verify unsupported resource/action combinations fail before confirmation or requests.
9. For paginated or enveloped responses, audit zero-item, singleton, and multi-item branches independently. Cardinality-based auto-selection or drill-down must not discard page metadata, future fields, raw JSON shape, or continuation state; require explicit selection when the command contract distinguishes listing a page from showing one item's detail.
10. When one resource family is removed from a mixed HTML page or command surface, inspect the full semantic ancestor, not only individual cards. Verify headings, empty-state copy, controls, pagination chrome, and explanatory text for the removed family are also absent, while unrelated resource sections remain. Require a realistic regression that asserts both absence of all removed-family residue and preservation of the retained family.
11. For destructive or irreversible workflows, verify the target reference is resolved, authorized, and canonicalized before the confirmation prompt. Invalid or ambiguous references should fail without prompting, and the prompt should name the exact canonical target that the confirmed action will affect. Canonicalize references with the same provider/resource rules used when listing or adding records before applying identity matching; equivalent spellings such as leading-zero numeric IDs must resolve to the same canonical identity, while the original input may be retained only for safe diagnostics. For a bulk action, a count alone is insufficient: show safe canonical title/ID labels for every captured target, or an equally unambiguous bounded representation that lets the user verify the complete selection. Require regressions for ambiguous, unknown, partial-but-unique, canonical, and equivalent-but-differently-formatted references; for bulk deletion, assert that a partial-reference prompt names every resolved target and that confirmation sends the frozen canonical IDs even if the catalog subsequently changes. Validate the success payload's semantically required result fields before reporting a mutation as successful: a missing or JSON `null` numeric count silently decodes to Go's zero value, so require presence explicitly (for example with a pointer field) and regress missing/null responses rather than claiming a successful zero-change operation.
12. For full-replacement edit APIs, compare every fetched field and submitted form key with the authoritative backend handler and model. Before prefilling or submitting an edit, require the fetched detail's canonical resource ID to match the ID resolved from the user's selected reference; project or tenant scope alone does not establish identity, and a same-scope mismatched response must fail without a mutation. Validate user-editable values locally when the backend normalizes invalid input, so typos cannot silently persist a fallback. Verify reference matching keeps ID, name, and alternate key as separate exact-match candidates rather than concatenating them. Require fresh post-save state for machine-readable success output and preserve partial refresh failures, but classify typed authentication and transport errors before generic saved-with-refresh-error handling so success reporting cannot suppress required recovery guidance. Assert raw plain output rejects ANSI, control, newline, and carriage-return injection. Add a regression that supplies a same-scope detail payload for a different resource and proves no prefilled edit or update request can target it.
13. For commands where option markers or separators may also be valid operand text, enumerate every plausible parse boundary before selecting a target. A separator fast path must compete with literal-value and longer-reference interpretations under the same ranking and ambiguity rules; it must not return early merely because one prefix resolves. Require collision regressions with multiple real resources that prove malformed or ambiguous input performs no detail or mutation request and cannot shorten or rebind the target.
14. For cleanup, invalidation, reset, cancellation, or error-transition changes, inspect the shared helper and every caller rather than only the patched path. Inventory direct `context.Background`, timeout, and cancellation construction plus nested resolver/confirmation closures, and distinguish interactive-only fallbacks from headless caller-owned paths. Verify buffered data is flushed or deliberately retained before timers, streams, projects, sessions, or scopes are invalidated. Treat scheduled timers as independent in-flight messages, and require regressions for stale timer delivery after a forced flush or ownership change. For multi-stage operations such as preview-then-save, exercise cancellation independently after every network stage has started, especially the persistence stage; proving only the preview request is canceled does not establish that teardown can stop an already-started mutation. For destructive commands, also cover cancellation while reference lookup is blocked and cancellation after lookup releases but before the mutation request, proving no mutation is sent.
15. For asynchronous state, verify stale results are rejected before any state mutation. Cover project and session transitions, overlapping submissions, completion events, reconnects, and cancellation boundaries that can reorder transcript or event output. Once an active turn has a correlation identity, treat identity-less same-scope events as unproven rather than compatible: test them both before and after acknowledgement, and ensure they cannot change status, append duplicate output, or settle the turn. When terminal status reconciles streamed output, do not assume its response snapshot is complete or newer: verify empty and shorter/lagging snapshots cannot erase or regress already accepted bytes, and require focused no-loss regressions.
   - For task-thread SSE identity guards that support aliased or unnamed frames, derive the discriminator from the normalized payload `type` when present and use the transport/SSE event name only when the payload discriminator is absent. Audit identity-less lifecycle and mirrored-chat frames across canonical, aliased, unnamed, and missing-payload-type cases; verify they cannot settle or mutate the owned turn while a matching execution identity still completes it.
   - For any async command that returns a generic result envelope (for example `resultMsg`) while targeting a task/thread or other replaceable view, carry the target identity and request/navigation generation in the message. Validate those identities before appending output or scheduling a refresh; session/project generations alone are insufficient because same-project navigation can still move the user to `/chat` or another task.
16. For transport-owned resources, assume `Close` can race with lazy `Open`, cancellation, or framework cleanup. Verify synchronization, cleanup-error propagation, waiter ordering, and compatibility of public error types and ordering. Treat metadata-to-open gaps as TOCTOU boundaries when metadata controls lengths, limits, or payload semantics.
17. For bounded JSON preview or serializer changes, load the companion `bounded_json_preview` skill and apply its semantic, adversarial, and allocation checks. In the audit verdict, specifically verify that bounds cover concrete fast paths and reflected paths, late errors and cycles remain detectable after the visible prefix fills, custom marshalers preserve invocation and ordering semantics, and tests compare against `encoding/json` rather than only happy-path fixtures.
18. Treat every rendered error string as untrusted terminal data, including client transport errors. Audit diagnostic wrappers, stored connection errors, status views, footer hints, and CLI/startup error wrappers together: transport errors may embed the complete configured request URL, while HTTP/backend errors may contain arbitrary response text, and a reachable configured-login failure can leak a raw `BaseURL` even when its backend error is generic. Redact URL userinfo, query parameters, fragments, and complete header-style credential values before rendering; `Authorization: Basic \u003cbase64\u003e` and `Authorization: Bearer \u003ctoken\u003e` must redact both scheme and payload, not merely a key/value token. Strip terminal controls and collapse layout-breaking whitespace from remaining diagnostics. Do not assume URL schemes are lowercase when matching embedded URLs: use case-insensitive scheme recognition or parser-based redaction, then test lowercase, uppercase, and mixed-case `HTTP(S)` URLs carrying userinfo, query secrets, and fragments. For combined connection states, retain sign-in-required precedence after a later transport failure without regressing remote recovery: an explicitly configured remote endpoint must still advise checking or correcting that remote URL, never local-start guidance, in both `/status` and the persistent hint. Require a regression for auth-required plus a remote transport failure and raw-output regressions using an authenticated/query-bearing request URL, a Basic authorization value, and ANSI/control/newline-bearing backend error text, rather than only synthetic harmless errors. Assert status diagnostics on the raw rendered string before stripping renderer-owned ANSI; a raw configured-URL sentinel alone does not cover controls originating in the diagnostic.
   - Do not assume the shared completion/error helper is safe merely because its authentication and transport branches sanitize diagnostics. Inspect its generic reachable/backend fallback and every output path, including interactive transcript entries and `firstError`/CLI serialization, so response-body text from mutation failures receives the same URL, credential, control-character, and layout redaction. Require a hostile backend-error regression for the generic branch, not only for connection-status wrappers.
19. For interactive commands that redact sensitive operands before parsing, trace tokenizer, redactor, transcript/history recording, and parser independently. Malformed arity cannot let the redactor stop before every potentially sensitive token is masked: exercise repeated empty quoted operands, an adjacent sensitive option and its operand, inline assignments, and dangling quotes. Regressions must assert local rejection, zero requests, and secret absence from raw view, transcript, and history.
20. Review tests for meaningful regression coverage rather than merely counting added cases. Verify each assertion observes the value before any helper normalizes away the defect. For terminal-safety tests, assert injected ANSI/control sequences are absent from raw rendered output before using helpers such as `stripANSI` for readability. For concurrency and timing regressions, inspect synchronization barriers and cleanup expressions literally: in Go, `defer release()` invokes `release` immediately when the defer is registered, while `defer func() { release() }()` defers the call; ensure a release channel or latch remains closed until after the overlap assertion and that cleanup cannot silently disable the condition being tested.
21. Distinguish multiline content from single-line metadata when reviewing terminal sanitization. A sanitizer that correctly preserves newlines for document bodies is unsafe for titles, paths, statuses, confirmation fields, or other layout-bearing values unless those separators are collapsed or rejected. Exercise `\n` and `\r` injection as well as ANSI escapes, bells, tabs, and other controls, and assert the raw output retains its intended line structure.
22. For allocation-focused parser or search rewrites, compare every optimized path against the prior parser's externally visible behavior. In particular, preserve metadata precedence, fallback content, and exact warnings for malformed or unterminated front matter, CRLF, and invalid UTF-8. Inspect invalid-input branches separately: a single invalid byte in a large line must not trigger whole-document string conversion, normalization, or lowercasing. Require regressions for both semantic equivalence and a large invalid-UTF-8 line; benchmarks that exercise only valid input do not prove the peak-allocation target.
23. For optimized JSON envelope or serializer paths that parse typed metadata while preserving raw payloads, separate syntax validity from typed metadata compatibility. If the prior behavior retained any syntactically valid JSON after compaction, a successful typed unmarshal is not an equivalent validity test: arrays, scalars, `null`, and objects with type-mismatched fields must retain raw data unless the contract explicitly excludes them. Compare byte-for-byte output and add focused regressions for each relevant valid non-object or type-mismatch shape, plus malformed JSON that must omit raw data.
24. Report every material bug, regression, missing requirement, or missing required validation. Do not fix findings in the audit turn.
25. If no material issue remains, explicitly state that the fresh strictly read-only audit found none.

## Follow-Up Discipline

- Fixes belong in a separate implementation turn. After fixes, stop and require a fresh audit from scratch.
- An audit that edits files, creates temporary/external outputs, or runs a modifying command is invalid and must not be used as the clean final review.
- If exact-HEAD validation evidence is missing or stale, report the evidence gap and stop without rerunning validation. The next non-audit turn must use `exact_head_validation_evidence` to validate the final target commit, attach and read back the Git note, and then trigger a fresh audit from scratch.
