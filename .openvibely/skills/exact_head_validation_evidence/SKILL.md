# Exact-HEAD Validation Evidence

Use this skill in a non-audit verification turn when a later strictly read-only review must independently verify that required checks passed for the exact commit under review.

## Procedure

1. Confirm the intended worktree, its `git rev-parse HEAD`, and a clean `git status --porcelain` before validation. If the request names an earlier audited or expected SHA, explicitly determine whether it requires that exact object or, instead, requires validation of the worktree's current `HEAD`. Do not silently validate a different commit, reset, or checkout: report the relationship and validate only the required object. When `HEAD` has advanced but the request explicitly calls for current-HEAD evidence, record the actual full SHA as the evidence target. Run assertions and validation in a fail-fast shell (`set -eu`; add `set -o pipefail` when using pipelines) so a failed SHA/status precondition cannot be followed by apparently successful command output.
2. Enumerate the intended focused test names from the target tree and verify that the exact `go test -run` selector matches every intended regression and no accidental omission. For regular expressions, check the selector against the actual `Test...` declarations or `go test -list` output before recording it; do not infer coverage from a similar-looking prefix or from the selector text itself. Compare the expected and observed names as unordered sets: `go test -list` output order is not a reliable source-order contract, so an order-sensitive assertion can falsely report a selector gap. On macOS/BSD hosts, use portable filtering such as `awk '/^Test/ {print}'` or `grep -E '^Test'` rather than GNU-only `sed` address/print syntax when extracting names. Record the literal selector and its verified match set in the note. If the selector is under-inclusive or misdescribed, rerun the corrected focused command and replace the evidence rather than relying on the repository-wide suite as a substitute for focused coverage. Then run feature-focused regressions followed by the required repository checks separately, recording the exact commands and outcomes. For this Go repository, the ordinary gate is `go build ./...`, `go vet ./...`, `go test ./... -count=1`, no output from `gofmt -l $(git ls-files '*.go')`, and `git diff --check`; add focused race coverage only when the change is concurrency-sensitive or explicitly requires it.
3. If acceptance criteria include a benchmark or performance measurement, run the exact benchmark command at the final target SHA and capture its actual output and environment. Record successful execution separately from performance interpretation: do not copy medians from memory or an earlier run as if they were observed in the current run, and label noisy reruns or prior same-commit measurements explicitly. Select the historical comparison ref from the implementation history, not merely `HEAD^`: a final commit may only add regression tests or evidence while its immediate parent already contains the optimization. Inspect the relevant ancestors and confirm that the named baseline actually predates the behavior being measured. For Go benchmarks with slash-separated subbenchmarks, validate the selector against the emitted benchmark names and fail the evidence step when a passing command runs zero intended subbenchmarks; overly restrictive slash matching can silently produce an empty benchmark result. If a benchmark helper logs custom samples, distinguish Go's calibration invocation from the final requested `b.N` samples and report the measured array/count rather than treating the calibration sample as part of the repeated evidence.
4. For absolute performance criteria, measure the criterion at the relevant boundary rather than substituting a proxy. For collection-byte requirements, capture actual response bytes for the affected endpoints and compare the same workload against the historical implementation or named baseline ref with the same harness; allocation `B/op` or a constant synthetic compact response is not a byte-reduction proof. For repeated fixed-delay latency, run multiple identical trials, retain the raw sorted durations, and report the observed median for both current and baseline paths. For peak RSS comparisons, compile the test binary from the exact target SHA, sample each named workload multiple times with the platform RSS tool, retain every sample, and use a conservative cross-sample comparison such as `max(larger-workload) - min(baseline-workload)` unless the acceptance criterion specifies another statistic. If existing tests cannot observe these metrics, add only narrowly gated test support that exercises the real end-to-end path; commit that support before final validation, and rerun all applicable checks at the resulting SHA. When a baseline worktree needs the committed harness copied or injected, state that explicitly, run the benchmark from the detached baseline worktree rather than the product checkout, and do not imply the harness existed in the historical ref.
5. Recheck that `HEAD` is still the validation target SHA and the product worktree remains clean. If either changed: do not promote the earlier results to exact-HEAD evidence. Resolve or commit the final product tree, then rerun every applicable check on the final SHA.
6. Do not commit the product changes after the checks and report those pre-commit results as validation of the new commit. A post-validation commit, even when believed content-identical, changes the evidence target unless exact tree equivalence is independently established; the safer handoff is to commit the final tree first and rerun the checks there.
7. Use the repository's accepted Git-notes mechanism to attach a concise note to that exact commit. State the full SHA, every passed command, the focused test command and its verified match set, and clean-worktree and unchanged-HEAD assertions. The note must contain the literal focused command and selector on the first write, not a placeholder such as `\\u003cselector above\\u003e` or a prose reference to an omitted command; inspect the assembled note text before `git notes add` to catch placeholder or quoting mistakes. Compose the note so literal command text such as `$(git ls-files '*.go')` cannot be expanded accidentally: use a single-quoted heredoc or equivalent shell quoting, then use `git notes add -f -m \\\"$note\\\" HEAD` only after all checks pass. For a simple note, prefer piping a single-quoted heredoc directly to `git notes --ref=refs/notes/commits add -f -F - \\\"$expected_sha\\\"`; this avoids fragile command-substitution/heredoc assembly while preserving literal shell syntax. Read the note back immediately from the exact SHA. For performance criteria, include the exact environment, raw observed samples or duration arrays, named baseline ref, and the calculation supporting the acceptance result. If the baseline did not contain the harness, the note must identify the committed target harness was copied or injected into the baseline checkout, name the source target commit/path and baseline ref, and state that baseline product files were otherwise unchanged; do not summarize this as simply using the same harness.
8. Read the note back with `git notes show \\\"$expected_sha\\\"` and report its target SHA, validation outcomes, clean final status, and any explicitly assessed relationship to a named prior commit. A later read-only audit can inspect that command without generating new evidence.
9. If a prior read-only audit reports exact-HEAD evidence unavailable, treat that as a hard handoff: select this skill in the separate validation turn, rerun all applicable checks on the final target SHA, attach and read back the Git note, and never promote the earlier console-only claim to exact-commit evidence.
10. For a cross-repository contract, bind the evidence to the actually delivered dependency ref, not merely a local predecessor or candidate. After delivery changes the dependency SHA, re-read or replace the consumer note so it names the delivered backend commit and ref; keep the consumer `HEAD`, test results, and note target unchanged unless the consumer itself changed. Compare the delivered dependency tree with the candidate/task tree before validation, and verify that every contract surface is present on the delivered ref: route registration, handler implementation and annotations, generated Swagger/API docs, repository/service behavior, and focused handler or route-contract tests.
11. When a repository-wide suite fails, separate changed-contract results from baseline failures. Re-run the focused changed-package checks independently, capture the exact failing test names and package paths, and reproduce material failures at the named parent or baseline ref when practical. Do not claim a clean suite from memory or infer that a failure is unrelated without a baseline comparison; record the distinction in the exact-HEAD note.
12. Treat the Git note as the handoff boundary. After attaching exact-HEAD evidence, do not continue implementation experiments in the same turn. If further work is unavoidable, any product-tree change invalidates the note until the final SHA is revalidated and the note is replaced; temporary experiments must be removed and `HEAD` plus clean status reasserted before relying on the note.

## Pitfalls

- Console assertions, memory, a clean tree, and checks that ran before a later commit, merge, rebase, or conflict resolution do not establish exact-HEAD validation.
- A focused `go test -run` regular expression can silently match fewer tests than its prose label suggests, especially when `Test` and resource prefixes are repeated. Verify the selector's actual match set against declarations or `go test -list` output, compare names order-independently, and treat any mismatch as an evidence gap requiring a corrected rerun and note.
- Go benchmark regexes use hierarchical slash matching; a selector that looks correct but matches no emitted subbenchmark names can still exit successfully. Inspect verbose benchmark output and assert that every intended case ran before recording results.
- A short SHA mentioned by an audit is not automatically the validation target if the verification task explicitly requires the current `HEAD`; preserve that distinction in the evidence and final report.
- If product files are modified but uncommitted, validation of the working tree is not validation of `HEAD`. Do not attach a note to `HEAD` claiming it covers those uncommitted changes; either validate the named commit separately or complete the repository's intended commit/delivery step before recording exact-commit evidence, and report the working-tree relationship explicitly.
- Do not create a tracked source artifact solely to record validation when Git notes are available. If evidence must be consumed outside this clone, ensure the relevant notes ref is preserved by the delivery process. A narrowly gated, committed harness is appropriate only when it directly measures a required acceptance criterion that existing tests cannot observe.
- The note must distinguish a successful zero-output formatting/diff check from merely listing those commands.
- Benchmark output is evidence only for the invocation that produced it. Keep observed output, prior same-commit measurements, and interpretation distinct when host contention makes timing unstable. When custom benchmark logging captures a calibration run plus the requested run, report the requested measured samples separately.
- Do not infer collection-byte reduction from allocation counts, labels, or a fixed synthetic compact response; measure the actual response boundary and a comparable historical path.
- Do not report an RSS result from a stale binary or a single favorable sample. Compile from the exact SHA, retain repeated samples for both workloads, and make the comparison statistic explicit.
- If an initial note expanded literal shell syntax, used a placeholder for a command or selector, or otherwise recorded commands inaccurately, overwrite the note only after confirming the actual checks and final SHA remain unchanged, then read the corrected note back.
- A task or candidate worktree can contain route annotations, generated docs, or repaired tests that are absent from the delivered/default dependency ref. Never treat the candidate diff or its passing tests as evidence for the delivered ref; compare files and run the focused contract checks after delivery.
- When a target-only performance harness is injected into a historical baseline, the evidence is incomplete unless the injection is explicitly recorded and the baseline product tree is shown unchanged. A narrative claim that both modes used the same harness is not enough for exact reproducibility. Run commands with the baseline worktree as the working directory; an otherwise successful command from the product worktree may run the wrong benchmark set or none at all.
- Some full suites exercise repository/worktree lifecycle or depend on generated/browser fixtures and can remove or invalidate a temporary validation checkout. Preserve logs outside the checkout, re-read the exact SHA and status from a stable repository root after each suite, and report missing fixtures or pre-existing failures explicitly rather than silently retrying or claiming a clean run.
- A failed shell assertion is not validation evidence if the shell continues into later commands. Use fail-fast options and verify the final command exit status before recording a note.
- When temporary baseline-harness cleanup is trap-based, do not assert cleanup-dependent status or path absence before the trap runs. Store benchmark output outside the checkout, let the cleanup shell exit, then verify harness removal, detached-worktree disposal, and product-tree cleanliness from a fresh shell.
- Post-note experiments create avoidable evidence risk. Perform optimization experiments before attaching the note; if an experiment changes product files, require a new final commit and complete evidence cycle rather than assuming a later restore or partial check proves equivalence.
- A benchmark comparison against the immediate parent can silently measure two optimized implementations when the final commit is an evidence-only or regression-test follow-up. Confirm the baseline is the last ref before the optimization, and record that relationship in the note.
- Validation helper commands must match the host shell's tool implementations: for example, GNU-specific `sed` address/print syntax can fail on macOS/BSD before any gate runs. Prefer portable `awk`/`grep` filtering and report a tooling failure separately from product validation.
